\chapter{Introduction}

\section{Project Motivation}

Data visualisation is an important technique for helping users understand complex datasets and discover meaningful patterns. However, many current data visualisation tools operate at a relatively low level of abstraction. In particular, users are often required to select tables, columns, transformations, and visual encodings directly from tabular data representations. This can be difficult for users who understand the real-world concepts in a domain, but are less familiar with the underlying database structure \cite{brientowards}.

A key limitation of this table-centred approach is that it often ignores the conceptual model of the data. Conceptual models, such as Entity-Relationship (ER) schemas, describe data in terms of entities, relationships, attributes, and cardinality constraints \cite{brientowards}. These structures can provide important guidance for visualisation selection. For example, a many-many relationship represents an association where one instance of an entity can be related to multiple instances of another entity, and vice versa. In the Mondial database, the relationship between countries and continents is an example: one continent contains many countries, while some countries may be associated with more than one continent. Such structures are often more suitable for network-based visualisations \cite{brientowards}, because the visualisation needs to show links between two sets of related entities. Therefore, reasoning over conceptual schema structures can help bridge the gap between how users understand data and how visualisation tools represent it internally.

To make this concrete, consider a user who wishes to see how the countries of the world are distributed across continents. In the Mondial database this information lives in the \texttt{encompasses} relationship, which records, for each country and continent, the percentage of that country's area lying in that continent. A conventional, table-centred tool inspects the selected columns and sees a place name and a percentage; recognising the place name as geographical, it will typically offer a symbol or choropleth map. Such a map is a poor fit for the question, because the relationship being asked about is the many-to-many association \emph{between} countries and continents, not a per-country quantity to be shaded onto a single map. A tool that instead reasons about the \emph{conceptual structure} of the selection, and recognises it as a many-to-many relationship, would offer a network-oriented view such as a chord diagram or an adjacency matrix, which shows the country--continent links directly. Figure~\ref{fig:intro-motivation} contrasts the two outcomes. This mismatch between what users conceptually intend and what table-centred tools recommend is the central problem this project addresses.

\phfig{0.9}{A table-centred tool recommends a geographic map for the country--continent \texttt{encompasses} relationship (left), whereas reasoning over the many-to-many conceptual structure recommends a chord or matrix view that shows the links directly (right).}{fig:intro-motivation}

Previous work by McBrien and Poulovassilis proposed the use of visualisation schema patterns to connect conceptual data structures with suitable visualisations. This approach has also been implemented and explored in earlier systems such as Bull's schema-driven visualisation tool \cite{bull2023visualisation} and Hannan's VizER system \cite{hannan2024vizer}. However, existing approaches mainly rely on manually designed rules or explicit pattern-matching procedures. With recent advances in Large Language Models (LLMs), there is an opportunity to investigate whether LLMs can perform this type of schema-level reasoning automatically.

This project explores the use of LLMs to reason over relational schemas, identify conceptual visualisation schema patterns, and select appropriate visualisations. Rather than requiring users to manually inspect tables and columns, the system supports a more intuitive workflow in which a user can express a visualisation request in natural language, and the system then retrieves the relevant data, identifies the underlying schema pattern, recommends a suitable visualisation, and generates an executable visualisation specification.

The project uses the Mondial database \cite{mondial} as its primary experimental environment. Mondial is a large geographical database containing entities such as countries, cities, provinces, rivers, lakes, and religions, together with rich relationship and cardinality information. Its well-documented schema and diverse conceptual structures make it a suitable benchmark for evaluating schema-level reasoning, visualisation schema pattern identification, and automated visualisation recommendation.


\section{Project Objectives}

The main objective of this project is to investigate whether Large Language Models can be used to support conceptual-model-based data visualisation. Using the Mondial database as a case study, the project focuses on whether LLMs can reason about relational schema information, including primary keys, foreign keys, and cardinality-related structures, and use this reasoning to identify appropriate visualisation schema patterns.


The project has four main objectives:

\begin{itemize}
    \item To represent the Mondial database schema in a machine-readable format that can be provided to an LLM as context.

    \item To evaluate whether LLMs can reason over selected tables and attributes and correctly classify them into visualisation schema patterns, including Basic Entity, Weak Entity, One-Many Relationship, Many-Many Relationship, and Reflexive Relationship.

    \item To investigate whether LLMs can recommend suitable visualisations based on the identified schema patterns and generate structured outputs that can be used by a visualisation library.

    \item To extend the current schema pattern identification approach towards an end-to-end natural-language-to-visualisation pipeline, including natural language query interpretation, data retrieval, visualisation recommendation, and visualisation specification generation.

    \item To realise this pipeline in a way whose deterministic core is reproducible and honest to evaluate, by having the language model author those programs once rather than answer each case at run time, and by keeping the ground-truth answers strictly separated from anything the LLM can see.
\end{itemize}

The initial stage of the project focuses on prompt-based schema reasoning over the Mondial database. Later stages will investigate visualisation generation and interaction. The project will also consider whether prompt engineering is sufficient for this task or whether training or fine-tuning a custom model is required.

The expected final output is a prototype system that demonstrates how LLM-based agents can assist data visualisation by using conceptual schema information rather than relying only on low-level tabular data. The success of the project will be evaluated through the accuracy of schema pattern identification, the appropriateness of visualisation recommendations, and the ability of the system to generate executable visualisations from user requests.

\section{Data Visualisation}
\subsection{The Grammar of Graphics}

Traditional visualisation systems are commonly organised around predefined chart types such as bar charts, pie charts, and line charts. In these systems, visualisation design is typically treated as the selection of a fixed chart template. However, this chart-centred approach limits flexibility and makes it difficult to represent more complex relationships within data. From a practical perspective, chart-based systems can only provide a limited number of predefined visualisations, making it difficult to support the diversity of real-world data analysis tasks \cite{wilkinson2005grammar}. In addition, treating each chart as an independent object often leads to unnecessarily complex system design, since similar graphical operations cannot be efficiently reused across different chart types \cite{wilkinson2005grammar}. Extending such systems with new visualisations therefore requires additional specialised code, reducing both flexibility and scalability. 

To address this limitation, Wilkinson introduced \textit{The Grammar of Graphics} \cite{wilkinson2005grammar}, which provides a formal and systematic framework for constructing visualisations through compositional rules rather than predefined chart categories. The concept of ``grammar'' was influenced by Chomsky's transformational grammar theory \cite{chomsky2002syntactic}, where grammar is defined as a formal system of rules capable of generating valid expressions in a language. Chomsky \cite{chomsky2014aspects} argued that diverse natural language expressions can be explained through an underlying deep grammatical structure, and Wilkinson extended this idea to statistical graphics. Under this framework, visualisations are interpreted as combinations of reusable graphical components and transformations instead of isolated chart types. This perspective enables diverse visualisations to be generated systematically from reusable primitives, while also revealing structural relationships between different visual forms. 

Wilkinson further organises visualisation generation into a sequence of interconnected and ordered components, beginning with the data source. The diagram~\ref{fig:fromdatatochart} illustrates how a chart is constructed within Wilkinson’s framework. Each stage of the process is explained below:

\begin{figure}[h]
\centering
\includegraphics[width=0.95\textwidth]{flowchart.png}
\caption{Data-flow diagram of chart construction in Wilkinson’s framework. Source: \cite{wilkinson2005grammar}.}
\label{fig:fromdatatochart}
\end{figure}

\begin{itemize}
    \item \textbf{Variables:} Variables are the data attributes selected from the original data source and a set of variables are called a \textbf{Varset} \cite{wilkinson2005grammar}. They determine what information will be represented, such as numerical measurements, categories, or labels. For example, variables such as population, income, or country name may be extracted from a dataset for further visual encoding. Transformations are included in this step to make meaningful statistical operations and enable the creation of new variables, aggregates, and other forms of summaries.

    \item \textbf{Algebra:} Algebra defines the operations that allow us to combine variables and specify dimensions of graphs \cite{wilkinson2005grammar}. Wilkinson proposed three basic operators that are necessary and sufficient for statistical graphics: cross, blend, and nest, which can be implemented in SQL through operations such as \texttt{INNER JOIN}, nested queries, and \texttt{UNION ALL}, respectively. Based on these fundamental operators, more complex operations can then be constructed, such as exponentiation and dot-cross. This determines the logical structure of the graphic before visual representation takes place.

    \item \textbf{Scales:} Scales maps a set of variables into visual measurement spaces \cite{wilkinson2005grammar}. It determines how numerical or categorical variables are translated into positions, sizes, colours, shapes, or other visual properties within a graphic. Wilkinson also introduces scale transformations, such as logarithmic and power transformations, which modify the representation of data while preserving important relationships. These transformations are not merely aesthetic adjustments, but analytical tools that help reveal patterns, compress extreme values, or improve interpretability.
    
    \item \textbf{Statistics:} Statistics are responsible for transforming raw data into more meaningful representational forms before graphical rendering \cite{wilkinson2005grammar}. These statistical methods, including bin, summary, region, smooth, and link, help reveal patterns, trends, and structures that may not be immediately visible in the raw dataset \cite{wilkinson2005grammar}. By integrating statistical computation into the visualisation grammar, graphics can represent both raw observations and derived summaries in a consistent and systematic manner.

    \item \textbf{Geometry:} Geometry defines the geometric objects used to represent data in a visualisation \cite{wilkinson2005grammar}. Wilkinson groups these objects into three categories: functions, partitions, and networks. Functions include points, lines, areas, intervals, and paths. Partitions divide data into regions using polygons and contours, and networks represent relationships through connected edges. By building graphics from a small set of geometric primitives rather than predefined chart types, its provides a flexible framework for creating diverse visualisations. Wilkinson also introduces collision modifiers, such as stacking, dodging, and jittering, to reduce overlap between graphical elements.

    \item \textbf{Coordinates:} Coordinates define the spatial framework in which geometric objects are displayed \cite{wilkinson2005grammar}. Wilkinson separates coordinate systems from geometric objects, allowing the same geometry to be represented in different ways through transformations of the underlying space. By treating coordinates as an independent component of the visualisation grammar, the same data and geometry can produce different visual representations without altering their underlying structure.

    \item \textbf{Aesthetics:} Aesthetics define the visual attributes used to perceive and distinguish geometric objects \cite{wilkinson2005grammar}. Wilkinson describes how data can be mapped to visual channels such as size, shape, colour, texture, and transparency, enabling graphical elements to convey additional information beyond their geometric position. By separating aesthetics from geometry, the Grammar of Graphics allows the same geometric structure to be represented through different visual encodings.

\end{itemize}

Another important aspect of the Grammar of Graphics is its declarative specification paradigm. Unlike imperative libraries such as Matplotlib, where users explicitly define drawing procedures step by step, declarative approaches describe the relationships between data and visual representations while leaving rendering details to the underlying system \cite{heer2010declarative}. Wilkinson formalised this idea through six specification statements: DATA, TRANS, SCALE, COORD, ELEMENT, and GUIDE. This framework has had a significant influence on modern visualisation systems, including ggplot2 \cite{wickham2011ggplot2, wickham2016ggplot2} and Vega-Lite \cite{satyanarayan2016vega}, which enable users to specify what should be visualised rather than how it should be rendered.

The Grammar of Graphics has become one of the theoretical foundations of modern visualisation specification languages and automatic visualisation systems. Many widely used visualisation frameworks are built upon its compositional and declarative design principles \cite{heer2010declarative}. By representing visualisations as structured combinations of reusable components, the framework enables computational reasoning over visualisation design and supports flexible visualisation generation beyond predefined chart templates.

This perspective is particularly important for this schema-based and LLM-driven visualisation project, where the objective is not only to select chart types, but also to reason over data structures, schema patterns, and visualisation composition. In this project, the Grammar of Graphics forms an important conceptual foundation for constructing visualisations and for exploring whether Large Language Models can perform schema-level reasoning to automatically generate appropriate visualisations.

\subsection{Visualisation Specification Languages}
Visualisation specification languages provide a structured and declarative approach to visualisation design. Instead of explicitly defining rendering procedures, users specify the relationships between data and visual encodings, while the underlying system determines how the visualisation is executed. By separating specification from execution, declarative languages simplify visualisation development while enabling system-level optimisation and cross-platform deployment \cite{heer2010declarative}. Most modern visualisation specification languages are influenced by Wilkinson’s Grammar of Graphics \cite{wilkinson2005grammar} or extensions of its underlying principles.

One of the earliest direct implementations of the Grammar of Graphics was GPL, used in IBM SPSS Statistics \cite{ibm2023gpl}. GPL introduced a formal grammar-based framework for specifying graphics through structured statements defining data sources, scales, guides, and graphical elements. However, GPL is considered relatively low-level and requires detailed specification from the user, resulting in a steep learning curve \cite{hannan2024vizer}.

To simplify the construction of statistical graphics, Wickham introduced ggplot2 and the concept of the layered grammar of graphics, an extension and reorganisation of Wilkinson’s Grammar of Graphics \cite{wickham2011ggplot2,wickham2016ggplot2}. Rather than introducing new graphical components, the layered grammar reorganises Wilkinson's framework around the concept of layers, where data, mappings, statistical transformations, and geometric objects are combined into self-contained visual units \cite{wickham2010layered}.  This layer-based structure simplifies the construction and modification of graphics while retaining the flexibility of grammar-based visualisation design. Nevertheless, ggplot2 is primarily designed for static statistical graphics and remains tightly coupled to the R programming language.

While grammar-based approaches focus on declarative visual specifications, D3 adopts a lower-level data-driven approach to visualisation design \cite{bostock2011d3}. Rather than introducing a new graphical grammar, D3 enables developers to directly bind data to native web document elements and manipulate them through JavaScript transformations. By operating directly on the Document Object Model (DOM), D3 provides exceptional flexibility, compatibility with existing web standards, and support for rich interaction and animation\cite{bostock2011d3}. However, this flexibility comes at the cost of increased implementation complexity, as users must explicitly specify visual structures and rendering behaviour. The expressive power of D3 made it highly influential for web-based visualisation, but its relatively low level of abstraction motivated the development of higher-level declarative grammars such as Vega \cite{vega2025} and Vega-Lite \cite{satyanarayan2016vega}.

Vega and Vega-Lite represent two influential declarative visualisation grammars that occupy different positions in the design space of visualisation specification languages. Vega is a low-level visualisation grammar that represents visualisations through structured JSON specifications, providing fine-grained control over data transformations, scales, graphical marks, and interactive behaviours \cite{vega2025}. This flexibility makes Vega suitable for highly customised visualisations and visual analytics systems, but often results in relatively verbose specifications. Vega-Lite was introduced as a higher-level grammar of interactive graphics that prioritises conciseness and rapid authoring \cite{satyanarayan2016vega}. It represents visualisations through compact encoding specifications and view composition operators while relying on rule-based defaults to infer unspecified details. Vega-Lite specifications are automatically compiled into lower-level Vega specifications, sacrificing some expressive power in exchange for substantially simpler and more readable specifications. Consequently, Vega and Vega-Lite illustrate the broader trade-off between expressive flexibility and specification simplicity in visualisation language design.

A different approach to visualisation specification was introduced through Tableau's VizQL \cite{mackinlay2007show}, which integrates data querying and visual specification within a single framework. Rather than requiring users to explicitly define queries or graphical properties, VizQL translates interactive actions, such as dragging fields onto rows, columns, or encoding shelves, into visual queries that simultaneously determine both the underlying database operations and the resulting visual representation. In this way, VizQL serves as a bridge between relational data and visualisation, describing not only how data should be displayed but also how the required data should be retrieved and aggregated. This abstraction significantly lowers the barrier to creating visualisations and laid the foundation for automatic visualisation recommendation systems.

Together, these languages illustrate the diversity of approaches to visualisation specification. GPL and ggplot2 extend the principles of the Grammar of Graphics through declarative grammar-based design, D3 emphasises direct manipulation and flexibility for web-based visualisation, Vega and Vega-Lite explore different trade-offs between expressive power and specification simplicity, while VizQL integrates visualisation specification with database querying. Despite their differences, all of these approaches aim to represent visualisations in a structured form that separates design intent from implementation details. This structured representation provides an important foundation for automated visualisation systems, enabling visualisations to be generated, analysed, and recommended programmatically.



\section{Conceptual Modelling of Relational Data}
\subsection{ER Schemas}
The Entity-Relationship (ER) schema is a conceptual modelling approach used to represent the semantics of an application domain independently of its implementation in a relational database. Rather than describing data in terms of tables and columns, the ER schema captures the conceptual structure of an application domain through entities, relationships, attributes, and cardinality constraints. Entities correspond to classes of real-world objects or concepts, relationships describe associations between entities, attributes provide descriptive information about entities or relationships, and cardinality constraints specify participation restrictions between related entities. These core components can be defined as follows:

\begin{itemize}
    \item \textbf{Entity:} An entity $E$ represents a set of objects that conceptually belong to the same type of thing. In ER schemas, entities are typically identified from nouns that describe the objects within the application domain \cite{mcbrien_er_modelling}.

    \item \textbf{Relationship:} A relationship $R$ represents a set of tuples of objects, where each tuple corresponds to a conceptual association between entities $E_1$, $E_2$. Relationships are commonly identified from verbs in the application domain \cite{mcbrien_er_modelling}.

    \item \textbf{Attribute:} Attributes describe the properties of entities or relationships \cite{ware2004information}. Attributes may be classified as mandatory, optional, or key attributes. Mandatory attributes are defined for every entity instance, optional attributes may be absent for some instances, and key attributes uniquely identify entities within an entity set \cite{mcbrien_er_modelling}.

    \item \textbf{Cardinality Constraints:} Cardinality constraints specify the minimum and maximum number of times an entity may participate in a relationship. An upper bound constraint defines the maximum number of relationship instances in which an entity can appear, while a lower bound constraint defines the minimum number of required participations \cite{mcbrien_er_modelling}.
\end{itemize}

In addition to entities, relationships, attributes, and cardinality constraints, ER schemas may also represent subset or ISA (is-a) hierarchies. A subset constraint indicates that the instances of one entity form a subset of another entity. For example, a \textit{manager} entity may be modelled as a specialised subset of the \textit{person} entity. Such hierarchies allow ER schemas to capture inheritance and specialisation relationships within a domain \cite{mcbrien_er_modelling}.

The followwing Figure~\ref{fig:ERmodel} illustrates a simple ER schema involving three entities denoted by rectangles: \textit{person}, \textit{department}, and \textit{manager}. The \textit{person} entity has three attributes: \textit{salary\_number}, \textit{name}, and \textit{bonus}. The underlined attribute \textit{salary\_number} represents the key attribute used to identify each person. The question mark after \textit{bonus} indicates that this is an optional attribute, meaning that a bonus value may not be recorded for every person. Similarly, the \textit{department} entity is identified by the key attribute \textit{dname}, while the \textit{manager} entity has an additional attribute \textit{mobile number}.

The diagram also contains a relationship, \textit{works in}, represented by a diamond between \textit{person} and \textit{department}. The cardinality constraint near \textit{person} is $1:1$, indicating that each person must participate in exactly one \textit{works in} relationship. In other words, every person works in one department. The cardinality constraint near \textit{department} is $0:N$, indicating that a department may have zero, one, or many persons associated with it.

The diagram further includes a hierarchy, represented by the arrow from \textit{manager} to \textit{person}. This indicates that every manager is also a person, but not every person is necessarily a manager. The \textit{manager} entity therefore specialises the \textit{person} entity by adding information that is specific to managers, such as the \textit{mobile number} attribute.

The ability of ER schemas to explicitly represent entities, relationships, attributes, and cardinalities makes them particularly suitable for schema-level reasoning. The concepts introduced above form the basis for the Mondial database, which is used throughout this project as the primary evaluation dataset. Mondial is a large geographical database containing entities such as countries, cities, provinces, rivers, lakes, languages, and religions, together with rich relationship and cardinality information. Its conceptual ER schema provides a realistic benchmark for evaluating schema-level reasoning and visualisation pattern matching.

\subsection{Visualisation Schema Patterns}
McBrien and Poulovassilis \cite{brientowards} proposed a set of visualisation schema patterns that establish a conceptual mapping between ER schema and visualisations. A visualisation schema pattern describes a recurring conceptual structure within an ER schema and the classes of visualisations that are suitable for representing that structure.

The approach is based on the observation that different ER structures naturally support different forms of visual representation. By matching subgraphs of an ER schema against predefined visualisation patterns, it becomes possible to identify visualisations that are structurally compatible with the underlying data model. This allows visualisation recommendations to be guided by conceptual schema information rather than solely by individual data attributes.

Based on an analysis of common visualisation techniques, five visualisation schema patterns were identified: Basic Entity, Weak Entity, One-Many Relationship, Many-Many Relationship, and Reflexive Relationship \cite{brientowards}. Each pattern corresponds to a particular ER structure and is associated with one or more visualisation types. Figure~\ref{fig:schema_patterns} summarises the five visualisation schema patterns and their associated visualisations.

\section{LLMs for Schema Reasoning and Visualisation}

Large Language Models (LLMs) have demonstrated strong capabilities in natural language understanding \cite{brown2020language}, reasoning \cite{wei2022chain}, code generation \cite{chen2021evaluating}, and structured prediction \cite{wang2025gpt}. Recent research suggests that these capabilities can be extended beyond traditional language tasks to support reasoning over structured data \cite{ye2023large}, database schemas \cite{yu2018spider,gao2023text}, and visualisation workflows \cite{dibia2023lida}. This section reviews the key concepts underlying the use of LLMs for schema reasoning and visualisation generation.

\subsection{Prompt Engineering and Structured Output}

Large Language Models (LLMs) can often be adapted to new tasks without additional model training through prompt engineering \cite{brown2020language}. More broadly, prompting has emerged as a new paradigm for natural language processing, often referred to as prompt-based learning \cite{liu2023pre}. Unlike traditional supervised learning, which directly learns a mapping from inputs to task-specific outputs, prompt-based learning reformulates downstream tasks into forms that resemble the language modelling objectives used during pre-training. By transforming an input into a carefully designed prompt, the LLM can leverage knowledge acquired during large-scale pre-training to perform new tasks with little or no task-specific training \cite{liu2023pre}.

Prompt engineering refers to the process of designing and refining prompts to guide an LLM towards a desired behaviour. A prompt may contain task instructions, contextual information, examples, constraints, or reasoning guidance that help the LLM interpret the user's objective and generate appropriate outputs. The quality and structure of prompts can have a significant influence on model performance, as prompts effectively define how a task is presented to the language model \cite{liu2023pre}.

The effectiveness of prompt engineering is closely related to the in-context learning capability of modern LLMs, whereby task-specific behaviour can be induced directly from information contained within the prompt rather than through parameter updates \cite{brown2020language}. Consequently, prompt engineering has become a widely adopted approach for adapting general-purpose language models to specialised tasks, including question answering, information extraction, reasoning, code generation, and data analysis.

Several prompting strategies have been proposed in the literature and are illustrated in Figure~\ref{fig:prompttype}. Zero-shot prompting provides only task instructions and relies entirely on the LLM's pre-trained knowledge to perform a task without demonstrations \cite{kojima2022large}. Few-shot prompting extends this approach by incorporating a small number of input-output examples within the prompt, enabling the LLM to infer the desired task format and behaviour through demonstration \cite{brown2020language}. Chain-of-thought (CoT) prompting further improves reasoning performance by encouraging the LLM to generate intermediate reasoning steps before producing a final answer, making complex reasoning processes more explicit and interpretable \cite{wei2022chain}. These prompting techniques have been shown to substantially improve performance across a wide range of reasoning and problem-solving tasks and have become fundamental components of many contemporary LLM-based systems.

    \centering
    \includegraphics[width=\textwidth]{prompttype.png}
    \caption{Examples of zero-shot, zero-shot-CoT, few-shot, and few-shot-CoT prompting. Adapted from Kojima et al.~\cite{kojima2022large}.}
    \label{fig:prompttype}
\end{figure}

For many applications, prompts are designed not only to guide model behaviour but also to constrain the format of generated outputs. Structured output prompting requires LLMs to produce responses in machine-readable formats such as JSON, SQL, or XML, enabling integration with external software systems and automated processing pipelines \cite{willard2023efficient}. This capability is particularly important in data-driven applications, where model outputs must often be consumed by downstream analytical or visualisation tools.

The ability of prompt engineering to elicit reasoning without additional model training is particularly relevant to this project. Different prompting strategies may significantly influence an LLM's ability to perform complex reasoning tasks and generate structured outputs. Consequently, prompt design forms a key component of the proposed approach and will be evaluated as part of the system development and experimentation.

\subsection{LLMs over Structured and Tabular Data}
Although large language models were originally developed for natural language processing tasks, they have increasingly been applied to structured and tabular data. A representative research direction is Text-to-SQL parsing, where a natural language question is translated into an executable SQL query over a relational database \cite{qin2022survey}. This task is important because it allows non-technical users to access relational data without manually writing SQL queries.

Text-to-SQL is not only a language generation task, but also a schema reasoning task. In order to generate a correct SQL query, the LLM must understand both the user's question and the structure of the underlying database schema. This includes identifying relevant tables and columns, linking natural language expressions to schema items, and reasoning over primary keys, foreign keys, column types, and join paths \cite{qin2022survey}. For example, if a question mentions provinces in a country, the LLM may need to infer that the province table should be joined with the country table through a foreign-key relationship.

Modern Text-to-SQL methods therefore place strong emphasis on schema linking and schema structure modelling \cite{qin2022survey}. Schema linking refers to the process of aligning words or phrases in the natural language question with tables, columns, or values in the database. Schema structure modelling, by contrast, focuses on the internal organisation of the database itself, such as which columns belong to which tables and how tables are connected through primary-key and foreign-key relationships. Recent approaches such as RAT-SQL \cite{wang2020rat}, SADGA \cite{cai2021sadga} and LGESQL \cite{cao2021lgesql} represent the question and database schema as graph structures, where nodes may correspond to question tokens, tables and columns, and edges encode relations such as table-column membership, foreign-key links, and question-schema alignments. This graph-based encoding allows models to reason explicitly over relational structure rather than treating the schema as a flat sequence of text.

Large benchmark datasets have played an important role in evaluating these capabilities. In particular, Spider \cite{yu2018spider} has become a standard cross-domain Text-to-SQL benchmark because it requires models to generalise to unseen databases and reason over complex schemas across different domains. Compared with earlier datasets such as WikiSQL \cite{zhong2017seq2sql}, which mainly contains simpler single-table queries, Spider better reflects the challenge of understanding multi-table relational schemas and generating complex SQL queries.

These developments are relevant to this project because they show that successful language-based interaction with structured data requires more than surface-level text understanding. Models must reason about the conceptual and relational structure behind the data. While Text-to-SQL systems aim to map natural language questions to SQL queries, this project focuses on mapping user intent and relational schema information to appropriate visualisation schema patterns. Therefore, research on schema linking, schema reasoning, and graph-based schema encoding provides an important foundation for using LLMs to support ER-driven visualisation recommendation.

\subsection{LLM-based Visualisation Systems}

Recent advances in Large Language Models (LLMs) have stimulated growing interest in applying language-based reasoning to visualisation tasks. Unlike traditional visualisation systems that often rely on handcrafted rules, specialised recommendation algorithms, or task-specific machine learning models, LLM-based approaches utilise prompt engineering to guide pre-trained models towards generating visualisations, visualisation specifications, or visual analytics insights.

An important precursor to this trend is NL4DV \cite{narechania2020nl4dv}, which translates natural language queries into analytic specifications consisting of relevant data attributes, analytic tasks, and Vega-Lite visualisations. Although developed before the widespread adoption of modern foundation models, NL4DV illustrates the importance of semantic interpretation in connecting user intent with visualisation generation.

Subsequent work explored the direct use of large language models for visualisation generation. Chat2VIS \cite{maddigan2023chat2vis} demonstrates that GPT-3 can generate visualisations directly from free-form natural language queries. By replacing complex natural language processing pipelines with prompt-guided code generation, the system highlights the potential of LLMs as end-to-end interfaces for visualisation authoring.

Similarly, LIDA \cite{dibia2023lida} extends the role of language models beyond visualisation generation to support multiple stages of the visualisation workflow. The framework combines dataset summarisation, visualisation goal exploration, visualisation generation, and infographic creation within a unified LLM-driven pipeline. This work demonstrates how prompt-guided reasoning can support not only chart generation but also higher-level visual analytics tasks.

LLM4Vis \cite{wang2023llm4vis} further investigates the use of prompting for visualisation recommendation. Instead of training task-specific recommendation models, the system converts dataset characteristics into natural language descriptions and employs few-shot prompting to recommend visualisation types and provide textual explanations for its recommendations.

Taken together, these systems demonstrate that prompt-engineered LLMs can effectively support visualisation generation, recommendation, and interaction. However, their reasoning processes remain primarily grounded in natural language descriptions, dataset summaries, and column-level data characteristics. Relatively little attention has been given to whether LLMs can reason directly over conceptual database schemas and their structural semantics.

\section{Related Work}

\subsection{Automated Visualisation Recommendation}

Automated visualisation recommendation seeks to assist users in selecting effective visual representations by automatically recommending chart types, visual encodings, or complete visualisation specifications. Research in this area has evolved from rule-based approaches towards machine learning and knowledge-driven recommendation techniques.

One of the earliest systems was Mackinlay’s APT \cite{mackinlay1986automating}, which formalised graphical design knowledge and selected visual encodings according to perceptual effectiveness criteria. This work established the idea that visualisation design principles could be represented explicitly and applied automatically.

Later systems such as Tableau Show Me \cite{mackinlay2007show}, Voyager \cite{wongsuphasawat2015voyager}, and Voyager 2 \cite{wongsuphasawat2017voyager} extended this rule-based paradigm by recommending visualisations based on attribute characteristics, partial visualisation specifications, and design constraints. These systems support exploratory data analysis by helping users navigate large visualisation design spaces and identify potentially useful visual representations.

Other approaches focus on identifying informative or interesting views within a dataset. SeeDB \cite{vartak2015seedb}, for example, recommends visualisations by identifying deviations between target and reference data distributions, automatically surfacing views that are likely to reveal meaningful patterns.

More recently, machine learning approaches have sought to reduce reliance on handcrafted rules. VizML \cite{hu2019vizml} formulates visualisation recommendation as a collection of prediction tasks, using statistical properties extracted from tabular datasets to infer chart types and visual encodings. KG4Vis \cite{li2021kg4vis} incorporates visualisation design knowledge through a knowledge graph representation, improving both recommendation quality and interpretability.

Consequently, recommendation decisions are typically based on data types, value distributions, correlations, cardinalities, and attribute names, with limited consideration of the conceptual structure of the underlying data model.

\subsection{Research Gap}

Automated visualisation recommendation systems have developed increasingly sophisticated methods for selecting visualisations from tabular data, progressing from rule-based systems to machine learning and, more recently, LLM-based approaches. However, these systems typically reason about attributes, values, and statistical properties rather than conceptual schema structures.

Conversely, conceptual modelling-based visualisation research has demonstrated that entities, relationships, weak entities, and cardinality constraints can provide valuable guidance for visualisation selection \cite{brientowards}. Nevertheless, existing implementations rely primarily on manually constructed rules and explicit pattern-matching procedures to identify visualisation schema patterns \cite{bull2023visualisation, hannan2024vizer}.

At the same time, recent advances in large language models have demonstrated strong capabilities in structured data understanding, schema reasoning, and prompt-guided decision making. Yet relatively little research has investigated whether these capabilities can be applied to conceptual schema analysis and visualisation schema pattern identification.

Therefore, this project investigates whether prompt-engineered LLMs can reason directly over conceptual schemas, identify visualisation schema patterns, and recommend appropriate visualisations based on conceptual relationships. By combining conceptual modelling with modern language models, the project aims to bridge the gap between schema-level semantics and automated visualisation design.

This project builds on two earlier implementations of the visualisation schema pattern approach. Bull's system \cite{bull2023visualisation} realised schema-driven recommendation using the Vega grammar and contributed a Java binding for authoring Vega specifications, while Hannan's VizER \cite{hannan2024vizer} implemented the five patterns as a hand-written rule engine within a full-stack web application offering both a data-first and a chart-first mode. Both encode the pattern-matching and chart-selection logic as manually maintained rules. The distinctive move in this work is not merely to replace those rules with a language model, but to have the LLM \emph{author} the deterministic rules once, as small, inspectable programs, and then execute those programs reproducibly. As Chapters~\ref{ch:approach} and~\ref{ch:evaluation} show, this framing directly targets the two failure modes that afflict a naive run-time use of an LLM: the bounded context window, which is dissolved by reading data from disk at run time rather than inlining it in a prompt; and library-version drift in generated visualisation code, which is pinned once per program rather than re-risked on every invocation.

\section{Application Design}
\label{sec:app-design}

The application of this project is designed to demonstrate, through a complete end-to-end implementation, the feasibility of the visualisation recommendation approach introduced in \emph{Towards Data Visualisation Based on Conceptual Modelling}\cite{brientowards}, while investigating how LLMs can support and enhance this approach by generating the program logic required to match data selections to visualisation schema patterns and identify appropriate visualisations.

\subsection{Design Requirements}
\label{sec:design-requirements}

Four requirements drive the design. First, from the user’s perspective, the system should be accessible and transparent. Users should be able to specify their data selection either manually or in natural language, receive executable visualisations without writing code, and understand why one chart is recommended over the available alternatives. Second, the system should be reproducible, where a given selection should always yield the same visualisation schema patterns and the same set of valid chart types, allowing users to trust the results and compare them across runs. Third, it should be honest when being evaluated. The system must never have access to the ground-truth answers against which it is evaluated. Fourth, it should be extensible. New chart types and schema patterns should be addable without disrupting components that already function correctly. As the following sections demonstrate, these requirements motivated the project’s central design decision of treating the LLM as a compiler that generates a program once, rather than as an executor invoked afresh for every case.

\subsection{Target Audience}
\label{sec:target-audience}

The system is aimed at two overlapping groups. The first is domain experts and non-technical users who understand the conceptual model of their data, the entities and the relationships between them, far better than its tabular, relational representation, and who are consequently poorly served by tools that reason only over columns and rows. By recommending visualisations from the conceptual structure of a selection, the system meets these users where their understanding already lies. The second is researchers and developers who need an auditable and extensible pipeline: because each pipeline step is a small, readable, deterministic program rather than an opaque per-case model call, its behaviour can be inspected, tested, and extended with confidence.

\section{The LLM-as-Compiler Paradigm}
\label{sec:llm-compiler}

An earlier version of this project prompted the LLM to process each case at run time, following an approach similar to that adopted by the LLM-based visualisation systems reviewed in the background section of Chapter~\ref{ch:approach}, including Chat2VIS \cite{maddigan2023chat2vis}, LIDA \cite{dibia2023lida}, and LLM4Vis \cite{wang2023llm4vis}. In this design, the LLM was invoked afresh for every request and was expected to interpret the selected data, determine an appropriate visualisation, and generate the corresponding output. Although this approach was flexible, it made the behaviour of the system dependent on a new model response for every case and exposed two well-known limitations of LLMs.

First, LLM outputs are non-deterministic. Even when the prompt, input data, and model configuration remain unchanged, repeated invocations may produce different schema-pattern classifications, chart recommendations, field mappings, or generated code. Such variation conflicts directly with the reproducibility requirement, according to which a given selection should always yield the same visualisation schema patterns and the same set of valid chart types. It also complicates evaluation because differences between runs may result from model sampling rather than from meaningful differences in the system being tested. From a user’s perspective, receiving different answers for the same selection may also reduce confidence in the reliability of the system.

Second, an LLM has a bounded context window. Inlining a complete dataset into a prompt requires the data to compete for limited context space with the system instructions, task description, schema information, examples, model reasoning, and generated output. This limitation becomes increasingly significant as the number of rows or columns grows. The input may need to be sampled or truncated, potentially removing values required to interpret the selection correctly, while the generated response may itself be truncated if insufficient context remains for a complete mapping or executable visualisation. Repeatedly transmitting large datasets also introduces avoidable token consumption and run-time overhead. More fundamentally, the size of the data should not determine whether the system can apply a visualisation rule that depends primarily on the conceptual structure of the selected tables and columns.

Following discussion with my supervisor, the project therefore adopted a different paradigm. Rather than asking the model to solve each individual case, the model is invoked once, at ``compile time'', to author a deterministic Python program that implements a complete pipeline step. The generated program captures the model’s interpretation and reasoning as explicit, reusable program logic. It can then be inspected, reviewed, revised, and tested before being incorporated into the system. At run time, the approved program is executed directly for every case, without requiring another model invocation.

This separation between compile-time authoring and run-time execution changes the role of the LLM. The LLM no longer acts as an executor whose answer directly determines the result of each request. Instead, it acts as a compiler that translates a high-level task specification into a persistent implementation. Once compiled, the same implementation is applied consistently to every input. The program reads its input data from disk at run time rather than receiving the data through the model prompt, thereby removing the dataset from the model’s context budget. Because the resulting program is a small and readable software artefact, its decisions can be traced to specific rules and branches, making the system substantially more auditable than a sequence of opaque, per-case model responses. This paradigm also makes direct use of the code-generation capabilities demonstrated by modern language models \cite{chen2021evaluating}.

The shift removes two independent sources of failure associated with the earlier run-time approach. The first is the context-budget axis. Since data is loaded by the compiled program at run time, the system is not constrained by the amount of tabular data that can be inserted into a model prompt, and no data must be omitted merely to satisfy a token limit. The second is the library-version axis. In a per-request generation approach, every model invocation may produce code based on different assumptions about library interfaces, available functions, or syntax. Under the compiled approach, these assumptions are resolved and tested once for each program, after which the approved implementation and its dependencies remain fixed. Compatibility risks are therefore addressed during development rather than being encountered repeatedly during user requests.

Each of the three principal pipeline stages is implemented according to this paradigm. The stages are realised as deterministic Python programs with explicit input and output contracts. The first program identifies the visualisation schema pattern represented by the selected data. The second determines the valid chart types and constructs explicit mappings between schema fields and visual roles. The third uses those mappings and the retrieved data to generate executable visualisations. Their contracts are aligned end-to-end, allowing the structured output of one stage to serve directly as the input to the next without case-specific prompts or intervening glue code. This modular structure also supports extensibility, since a new schema pattern or chart type can be introduced within the relevant program without requiring the rest of the pipeline to be regenerated.

At compile time, the LLM authors one deterministic Python program per stage, mainly a ER pattern classifier, a chart recommender, and the family of renderers. These Python programs are then frozen as ordinary source files and treated exactly like any other deterministic component of the system (Section~\ref{sec:llm-compiler}).

At run time, a request flows through those frozen programs in a fixed order. The entry point is a data selection, with a base table together with a set of selected columns, optionally accompanied by filters, joins, and an aggregate. The system accepts this selection through either of two doors: the user may pick a base table and columns directly in the web front end, or express the request in free-text natural language query, which the LLM parses into the same validated selection (Section~\ref{sec:nl-front-end}). Offering both a structured and a natural-language route onto a single pipeline is a capability the LLM affords, and it is what sets this system apart from prior visualisation tools built on the same schema-pattern foundation, which typically expose only a fixed structured interface. 

The validated selection is first passed to the classifier, which identifies its visualisation schema pattern. The recommender then uses this pattern and the underlying rows to determine the compatible chart types and produce a field-to-role mapping for each candidate. Finally, the corresponding renderers read the rows and mappings to generate runnable HTML visualisations, which are returned to the user by the server. The schema and rows are read from a live PostgreSQL database, the same source used in both the experiments and the deployed system. The rows are retrieved through a single read-only, parameterised SQL query authored at compile time, which returns them in the row-dictionary format the rest of the pipeline consumes. Beyond parsing the request at the entry point, the only other run-time use of the LLM is the chart selection of Section~\ref{sec:step2-llm}, which tailors the recommendation to the user's stated intent from within the legal candidate set.


\section{Natural-Language Front End}
\label{sec:nl-front-end}

The entry point to the run-time pipeline is a data selection, and a user may supply it in one of two ways: by choosing a base table and columns directly in the web front end, or by expressing a request in natural language that a semantic parser translates into the same validated selection. The parsed selection, a structure of the form \{table, columns, joins, filters, aggregate\}, is exactly what the data-retrieval layer consumes, so the natural-language layer changes only how the selection is produced, never what the rest of the pipeline does with it. The model may only choose data; it may never name a pattern or a chart, and every table and column it returns is validated against the schema before use.

\paragraph{Text-to-selection, not Text-to-SQL.}
An earlier version of the project envisaged this stage as a Text-to-SQL component, in which a language model would translate each free-text request directly into an executable query. The implemented system deliberately adopts a narrower approach. The model produces only a validated \emph{data selection}, represented by the structure \{table, columns, joins, filters, aggregate\}, and never generates SQL directly. Query construction remains the responsibility of the compiled builder described in Section~\ref{sec:step0}. This is a substantive design decision based on four related considerations.

The first is verifiability. A complete Text-to-SQL query must resolve operations such as join paths, filters, and aggregations from the user’s request. Although the resulting query may be syntactically valid, it can still be semantically incorrect. For example, an inappropriate join or aggregation may return plausible-looking but incorrect rows without producing an explicit error. By contrast, a data selection is a small, closed structure whose tables, columns, joins, filters, and aggregate operations can be validated individually against the database schema before execution.

The second consideration is safety. Allowing a language model to generate arbitrary SQL for execution against a live PostgreSQL database introduces operational risks. Restricting the model to a structured selection allows the compiled query builder to enforce a limited query grammar, validate all referenced schema elements, parameterise filter values, and issue only read-only, timeout-bounded queries. Consequently, malformed or unsupported requests can be rejected before they reach the database.

The third consideration is determinism. SQL generated afresh by a language model may vary between otherwise identical requests and may change as the underlying model is updated. In the implemented design, the model authors the query-building program only once at compile time. At run time, this fixed program translates validated selections into SQL, ensuring that the same selection produces the same query. The data-retrieval layer therefore follows the same LLM-as-compiler paradigm as the remainder of the pipeline.

The fourth consideration is the separation between model input and the experimental ground truth. The language model determines only \emph{which data} the user intends to visualise; it neither identifies a visualisation schema pattern nor selects a chart type. These decisions remain the responsibility of the classifier and recommender. The model therefore cannot pass a pattern or chart answer into the evaluated pipeline, preserving the experimental separation described in Chapter~\ref{ch:evaluation}. The resulting division of labour is deliberate: the language model performs the ambiguous linguistic task of mapping a request to a structured data intent, while a deterministic and verifiable program performs the mechanical task of constructing the corresponding query.

This natural-language parser is one of two components for which the deployed system consults a language model at run time, the other being the LLM-assisted chart-selection component described in Section~\ref{sec:step2-llm}. By contrast, the classifier, data-retrieval layer, and renderers described in Sections~\ref{sec:step0}--\ref{sec:step3} execute without run-time model calls. The structured picker provides an alternative input route, allowing users to specify the same validated data selection directly by choosing the required table, columns, joins, filters, and aggregation through the interface.



\section{Data Retrieval by a Compiled SQL Builder}
\label{sec:step0}

Both the structured picker and the natural-language parser described in Section~\ref{sec:nl-front-end} produce the same validated data selection in the form {table, columns, joins, filters, aggregate}. A selection, however, specifies only the data that the user wants and does not contain the data itself. Realising that description as concrete rows is the task of the data-retrieval layer, the SQL builder. Given a selection, it composes a single SQL query that performs the join, the filtering, and any aggregation inside the database, executes it against the live PostgreSQL database, and returns exactly the row dictionaries that the rest of the pipeline consumes. It is therefore the bridge between the abstract selection the front end produces and the concrete rows that pattern identification, chart recommendation, and rendering all read. Since the row shape it returns is identical, no matter where the rows come from, nothing downstream depends on how they were fetched.

Performing this work in the database, rather than fetching whole tables and processing them in the application, matters for two reasons. First, it is exact. An aggregate such as a per-group sum is computed over the entire table, not over a bounded sample of rows pulled back into memory, and the same is true of the column statistics that populate the filter controls. Second, it is economical. Only the rows the selection actually needs cross the network. Because the query returns the identical row shape either way, none of the downstream reasoning changed to gain these properties.

Crucially, the LLM does not generate a new query for each request. Following the same paradigm as the three pipeline stages described in Section~\ref{sec:llm-compiler}, the LLM is invoked once at compile time to author a deterministic SQL builder. Given the cleaned schema and a validated selection, this program generates a parameterised query. This program reasons only from the schema and the selection, without access to gold-standard labels, thereby preserving the experimental separation from the ground truth at the data-retrieval layer. To ensure safe database access, filter values are bound as query parameters rather than interpolated into the SQL text, and all table and column identifiers are validated against the schema before use. Each query is executed within a read-only transaction and subject to a statement timeout, preventing data modification and limiting the risk of excessively expensive execution.

\section{Visualisation Schema Pattern Identification}
\label{sec:step1}

Once the data has been retrieved, the pipeline classifies the selection into one of six visualisation schema patterns: basic entity, basic entity inherited key, weak entity, one many relationship, many many relationship, and reflexive many
many relationship. This refines the five-pattern taxonomy of McBrien and Poulovassilis \cite{brientowards} by drawing out, as a named special case of the basic entity, the entity whose entire primary key is inherited from a parent as a foreign key (an is-a specialisation). As explained below, this case is visualised exactly like a basic entity but is named separately because, structurally, it sits on the boundary with the weak entity and the many-to-many relationship and must be told apart from them during classification.


Classification reasons purely from the primary-key (PK) and foreign-key (FK) structure of a selection, never from its retrieved rows or from the natural-language meaning of table or column names. It therefore depends only on the selection itself, not on the data returned by the retrieval layer of Section~\ref{sec:step0}. That layer runs first in the pipeline solely because the data-aware steps downstream (chart recommendation (Section~\ref{sec:step2}) and rendering) require the data rows, and not because classification does. Crucially, only the selected columns count. 

A foreign key is relevant only when its column is one of the selected columns, and a primary-key column counts only when it is selected. The minimum meaningful selection is a primary key together with at least one further attribute, so that there is something to plot. The six patterns are identified as follows, with examples drawn from the Mondial database used throughout this project.



\paragraph{Basic entity.} A basic entity does not depend on any other entity. For a basic entity, none of its selected columns is a foreign key, so the selection is simply a primary key and one or more attributes. For example, selecting \texttt{code} and \texttt{population} from the \texttt{country} table, or \texttt{name}, \texttt{elevation} and \texttt{depth} from \texttt{lake}, yields a basic entity, because neither table's selected key columns link to another table.

\paragraph{Basic entity with inherited key.} McBrien and Poulovassilis \cite{brientowards} note that the whole primary key of an entity may be inherited as a foreign key from a single parent, modelling an is-a specialisation. This is identified when every primary-key column is itself a foreign key to one parent, leaving no local key column of its own, and the single-column case counts too. Selecting \texttt{country}, \texttt{gdp} and \texttt{unemployment} from the \texttt{economy} table is an example from Mondial database. \texttt{country} is the entire primary key and is inherited from the \texttt{country} entity, so \texttt{economy} specialises \texttt{country}. 

Conceptually it remains a basic entity, since it satisfies the definition that a single entity described by a key and its attributes, and for the purpose of visualisation it is treated as exactly that, sharing the basic-entity chart family of Section~\ref{sec:step2}; its inherited key is still a perfectly good identifier to plot against. It is nonetheless named as a pattern in its own right for one reason: an all-foreign-key primary key is, at a glance, structurally indistinguishable from a weak entity (where only \emph{part} of the key is a foreign key) and from a many-to-many relationship (whose key is \emph{two} foreign keys to different parents), both of which also build their key out of foreign keys. A classifier that did not handle this case explicitly would therefore readily misfile it as one of those. Giving it its own label pins that boundary precisely --- and it is, empirically, the case that weaker program authors found hardest to classify correctly. It is thus best understood not as a seventh kind of thing but as a labelled special case of the basic entity, separated for classification rather than for visualisation.

\paragraph{Weak entity.} A weak entity depends on a parent entity and has a compound primary key in which a proper subset of the key is a foreign key to a single parent, while at least one remaining primary-key column is local to the child. Selecting \texttt{country}, \texttt{year} and \texttt{population} from \texttt{country\_population} is an example from Mondial database. \texttt{country} is a foreign key to the \texttt{country} table, and \texttt{year} is local to the child, so the two together form the compound key. The \texttt{ethnic\_group} table (key \texttt{country} plus \texttt{name}) behaves the same way.

\paragraph{One-many relationship.} A one-to-many relationship is identified when the selection contains a foreign key to a single parent that is not part of the table's own primary key, and so acts purely as a link. \section{Chart Recommendation and Mapping}
\label{sec:step2}

With the selection's pattern identified, the pipeline translates it into a set of compatible chart types and an explicit mapping from the selected columns to the visual roles used by each chart. As with the classifier, this process is implemented by a program authored once by the LLM at compile time. The program determines the type of each selected attribute from its SQL type, checks the mandatory requirements of each candidate chart against the pattern rules, and produces a mapping whose field names correspond exactly to those expected by the renderers in the next stage. These fields include \texttt{source}, \texttt{target}, \texttt{value}, \texttt{category}, \texttt{x}, \texttt{y}, and \texttt{size}. This strict field-name contract allows each mapping to be passed directly to its corresponding renderer without further adaptation.

The identification of compatible charts proceeds in two stages. First, the visualisation schema pattern identified in the preceding step determines the initial group of candidate charts. Second, the system narrows this group by classifying the selected columns according to their data types. Following McBrien and Poulovassilis \cite{brientowards}, each column is assigned to a dimension based on its SQL type. A scalar dimension contains values with a natural ordering, such as integers, floating-point numbers, timestamps, and dates. It is typically represented through a visual channel of a mark, including position, length, area, or a continuous colour scale. A discrete dimension contains a limited set of values that may be ordered or unordered. It may determine the choice of mark or vary a visual channel such as a categorical colour key.

Some chart types impose more specific semantic requirements that cannot be represented by the scalar and discrete distinction alone. A calendar chart requires a temporal attribute, a word cloud requires a lexical key, and a choropleth map requires a geographical key. Since lexical and geographical meaning cannot always be determined reliably from SQL types alone, charts with such requirements are marked as conditional candidates. How a key is actually judged to be geographical or lexical is a matter of implementation, deferred to Section~\ref{sec:impl-geo}. Each compatible chart is returned with a mapping that specifies the role assigned to every selected column. The pattern-specific descriptions below connect the abstract dimensions of each schema pattern, denoted by $k$, $a_1$, $a_2$, and so forth, to the concrete field names used in these mappings. Each description is accompanied by a summary table based on the format used in \cite{brientowards} and extended to include the mapping fields produced by this project.



\paragraph{Basic-entity charts.} Having no foreign-key dependency, a basic entity is the conceptual model of a single table, and it supports the richest group of charts, gated by how many scalar attributes accompany the key $k$:
\begin{itemize}
  \item Bar chart --- represents each instance as a bar whose length is a single scalar attribute $a_1$; mapped as (\texttt{key}, \texttt{measure}). It is capped at a subjective upper cardinality for legibility.
  \item Scatter diagram --- plots each instance as a point positioned by two scalars $a_1,a_2$ (\texttt{x}, \texttt{y}), with an optional further scalar as a colour channel.
  \item Bubble chart --- extends the scatter diagram with a third scalar $a_3$ as the point's size (\texttt{x}, \texttt{y}, \texttt{size}), and an optional fourth scalar as colour.
  \item Calendar chart --- shades one day cell per instance from a temporal attribute (\texttt{date}, \texttt{key}).
  \item Choropleth map --- colours one geographical region per instance, so it is offered conditionally when the key is geographical (\texttt{region}, \texttt{color}).
  \item Word cloud --- draws one word per instance sized by a scalar, offered conditionally when the key is lexical (\texttt{text}, \texttt{size}).
\end{itemize}

\paragraph{Weak-entity charts.} A weak entity has a compound key, with one part $k_1$ (the parent it is attached to) identifies a set of tuples, and the second part $k_2$ identifies a tuple within that set. Its charts are therefore grouped or small-multiple forms in which the $k_2$ values are compared across the $k_1$ groups on a shared scalar attribute $a_1$:
\begin{itemize}
  \item Line chart --- draws one line per $k_1$, plotting the scalar child key $k_2$ on the $x$-axis and $a_1$ on the $y$-axis (\texttt{series}$=k_1$, \texttt{x}$=k_2$, \texttt{y}$=a_1$).
  \item Stacked bar chart --- draws one bar per $k_1$ with a stack element per $k_2$ (\texttt{group}$=k_1$, \texttt{segment}$=k_2$, \texttt{value}$=a_1$).
  \item Grouped bar chart--- clusters the $k_2$ bars within each $k_1$, using the same mapping as the stacked form.
  \item Spider chart --- draws one ring per $k_1$ and one spoke per $k_2$, the intersection set by $a_1$ (\texttt{ring}, \texttt{spoke}, \texttt{value}).
\end{itemize}
Whether all of these forms apply depends on a further property of the weak entity, its completeness. A weak entity is complete when every $k_1$ group carries the same set of $k_2$ values, so that the groups can be laid side by side against one common set of positions. This matters because the stacked bar and spider forms compare groups across a shared axis of $k_2$ values, as a stacked bar places the same stack elements in every bar, and a spider chart draws the same spokes on every ring, so both are only meaningful when those elements and spokes denote the same thing in each group. In Mondial the contrast is clear. The \texttt{country\_population} table (key \texttt{country} plus \texttt{year}) tends towards completeness, because population is recorded against a common, regular set of years, so the years form a shared axis across countries. Having the scalar key, they also suit the line chart, which plots population against year directly. The \texttt{ethnic\_group} table (key \texttt{country} plus \texttt{name}) is the opposite. Since each country has its own distinct set of ethnic groups, there is no shared set of $k_2$ values to align, and a stacked or spider comparison across countries would place unrelated groups in the same position. The line and grouped-bar forms therefore carry no completeness requirement, whereas the stacked and spider forms are offered only when the weak entity is complete.

\paragraph{One-many charts.} A one-to-many relationship is hierarchical. The entity on the ``many'' side is the parent $E_p$ and the other the child $E_c$, so the charts are containment or tree forms:
\begin{itemize}

  \item Circle packing --- nests child circles inside a parent circle, sized likewise, with the same mapping.
  \item Hierarchy tree --- connects parent nodes to child leaves by lines, encoding structure alone; it requires no scalar attribute and maps as (\texttt{parent}, \texttt{child}).
\end{itemize}

\paragraph{Many relationship charts.} For the two many-to-many patterns the data that governs the visualisation lives on the relationship between the two entities $E_1$ and $E_2$, so the charts are node-link and matrix forms over the two primary-key foreign keys (\texttt{source}, \texttt{target}). The paper proposes the first two, and this project adds the remaining three to cover the dense, large, and attribute-free relations that node-link diagrams handle poorly:
\begin{itemize}
  \item Sankey diagram --- left elements are instances of $E_1$, right elements instances of $E_2$, and flow width a scalar $a_1$ (\texttt{source}, \texttt{target}, \texttt{width}).
  \item Chord diagram --- perimeter points joined by ribbons whose width is the scalar $a_1$ (\texttt{source}, \texttt{target}, \texttt{width}).
  \item Matrix heatmap --- an adjacency grid with one row per $E_1$ instance and one column per $E_2$ instance, each cell shaded by the weight of the pair it represents (\texttt{source}, \texttt{target}, \texttt{value}), with an optional discrete attribute tinting the cells.
  \item Force-directed graph --- a physics layout in which each entity instance is a node and each relationship a link whose weight is that of the pair (\texttt{source}, \texttt{target}, \texttt{value}).
  \item Arc diagram --- the same nodes placed along a single line and joined by semicircular arcs whose thickness is the weight of the pair (\texttt{source}, \texttt{target}, \texttt{value}).
\end{itemize}
In all three the \texttt{value} field plays the role that \texttt{width} plays for Sankey and chord. It carries the relationship's scalar attribute $a_1$ whenever one was selected, so that the cell shade, link strength, or arc thickness encodes $a_1$ directly. Many relationships, such as \texttt{is\_member} and \texttt{merges\_with}, simply record that two entities are related and contain no additional attributes, leaving no $a_1$ to visualise. In such cases, the edge weight defaults to the number of rows associated with each pair. For a simple relationship, this count is one for every existing link, so the resulting visualisation encodes the adjacency structure itself. The renderers signal this by reading the literal string \texttt{"count"} in the \texttt{value} field in place of a column name. This fallback is what lets the matrix, force, and arc views represent attribute-free relations at all, whereas Sankey and chord, which must map a scalar onto ribbon width, cannot be drawn without an $a_1$.

Whereas the original pattern (Table~\ref{tab:step2-relationship}) offers a fixed menu, a relationship selector measures three properties from the rows themselves: the \emph{density} of the relation (distinct edges divided by $|E_1|\times|E_2|$), its size $N$ (the larger of the two node sets), and how \emph{symmetric} it is (the share of mutual pairs). It then ranks charts by an ordered rule table. A node-link view (Sankey or chord) leads only while the relation is sparse, small, and carries a scalar width; once the relation becomes dense or large, the matrix heatmap leads instead, because node-link diagrams become visually unreadable in that regime. The decision thresholds are explicit constants ($\texttt{DENSE}=0.10$, $\texttt{LARGE\_N}=200$, $\texttt{SYMMETRIC\_MIN}=0.6$), keeping the selector inspectable and its behaviour reproducible.


\subsection{LLM-assisted chart selection}
\label{sec:step2-llm}

The chart-recommendation process described above is entirely deterministic and produces the set of valid chart candidates together with their field-to-role mappings. In the deployed system, the final selection of the preferred candidate is assisted by an LLM, consistent with the project’s objective of investigating how language models can enhance visualisation recommendation. This assistance is enabled by default whenever an LLM is available, while the deterministic reference choice is used otherwise. The model can select only from candidates approved by the deterministic recommender and cannot introduce a new chart type or construct a new mapping. The structural contracts of the pipeline therefore remain intact, although the choice of the preferred chart may vary between model invocations. This layer is model-agnostic and can be served by any sufficiently capable LLM. The model used and its configuration are consequently treated as implementation choices, as discussed in Section~\ref{sec:impl-llm-select}.

The LLM receives the complete set of deterministic candidates, each accompanied by a brief description, as well as the user’s stated intent and a collection of deterministic signals derived from the retrieved rows. The intent is treated as a soft objective, while the data signals include the number of rows, the cardinality and proportion of null values for each column, and the ranges of numeric attributes. Using this information, the model ranks the candidates, identifies one as the preferred chart, and provides a concise explanation of its choice. It may also reassign a selected column to an existing expressive role, such as a measure or an axis, when this improves alignment with the user’s intent.

The model’s freedom is intentionally constrained. It cannot introduce a chart type, mapping field, or column name that is absent from the deterministic input, nor can it alter fixed identity or relationship roles, such as entity keys or the two endpoints of a relationship. It also receives no gold-standard label. The model therefore operates only within the candidate and mapping space already judged valid by the deterministic recommender, preserving the validity of the pipeline and its separation from the evaluation ground truth. The preferred chart itself is intentionally not deterministic because this judgement is the specific responsibility delegated to the LLM. By considering both user intent and properties of the retrieved data, the layer allows the same selected columns to produce different preferred charts for different analytical goals or data scales. Its implementation is described in Section~\ref{sec:impl-llm-select}.



\section{Visualisation Generation}
\label{sec:step3}

The preceding step produces a set of valid chart candidates for the selection's identified visualisation schema pattern, each accompanied by a complete field-to-role mapping. The LLM then highlights one candidate as its recommendation. In this final stage, the candidates are rendered as executable, interactive HTML visualisations using D3~v7 \cite{bostock2011d3}. The recommended chart is rendered and returned by default, while the remaining valid candidates remain accessible and will be rendered by the same mechanism when selected by the user. As with the classifier and recommender, each renderer is authored once by the LLM at compile time rather than generated afresh for every request.

D3 was selected in preference to the higher-level declarative grammars reviewed in the background, including Vega and Vega-Lite \cite{satyanarayan2016vega,vega2025}. Several visualisation chart types require specialised and highly interactive layouts, including chord diagrams, adjacency matrices, arc diagrams, and force-directed graphs, for which D3 provides more direct and fine-grained control. % Fixing a single library version at compile time also avoids the version-drift failures examined in Chapter~\ref{ch:evaluation}.

The renderers are authored through a modular prompt design rather than a separate monolithic prompt for each chart type. Every chart shares a common D3~v7 base prompt that defines the library version, the uniform \texttt{render(mapping, rows)} entry point, the use of the mapping's \texttt{table} field to identify the relevant grouped data, and the requirement for interactive behaviour. Each chart type also has a concise supplementary prompt containing only its specific rendering requirements. The base prompt and chart-specific prompt are combined to author the corresponding renderer. Maintaining the shared contract in a single location allows corrections to be applied consistently across all chart types. It also enables new charts to be added through an additional chart-specific prompt without modifying existing renderers, thereby supporting the extensibility requirement. The implementation of this prompt-composition process is described in Section~\ref{sec:impl-renderers}.

Because the renderers load data at run time rather than receiving it through the prompt, their generation is not constrained by the size of the dataset. Fixing the D3 version in the base prompt also prevents the renderers from relying on deprecated interfaces encountered under the earlier run-time generation approach. Renderers were implemented for all applicable visualisation schema patterns and cover the eighteen chart types that the recommendation stage can propose. The following subsections describe how each renderer interprets the mappings:

\paragraph{Basic-entity renderers:}
\begin{itemize}
  \item Bar chart --- one bar per entity instance, its length the scalar measure.
  \item Scatter diagram --- each instance a point positioned by two scalars.
  \item Bubble chart --- as the scatter, with a third scalar as the point radius.
  \item Calendar chart --- one shaded day cell per instance according to a temporal attribute.
  \item Choropleth map --- each geographical region coloured by its attribute.
  \item Word cloud --- each key drawn as a word sized by the scalar attribute.
\end{itemize}

\paragraph{Weak-entity renderers:}
\begin{itemize}
  \item Line chart --- one line per parent $k_1$ across the child key $k_2$.
  \item Stacked bar chart --- one bar per $k_1$ segmented by $k_2$.
  \item Grouped bar chart --- the $k_2$ bars clustered within each $k_1$.
  \item Spider chart --- one ring per $k_1$ and one spoke per $k_2$, the intersection set by the scalar attribute.
\end{itemize}

\paragraph{One-many renderers:}
\begin{itemize}
  \item Treemap --- child rectangles nested inside a parent rectangle, sized by the measure.
  \item Circle packing --- child circles nested within a parent circle, sized likewise.
  \item Hierarchy tree --- a node-link tree connecting each parent to its child leaves.
\end{itemize}

\paragraph{Many relationship renderers:}
\begin{itemize}
  \item Sankey diagram --- flows from source nodes on the left to target nodes on the right, the width the scalar attribute.
  \item Chord diagram --- nodes on a circle joined by ribbons of that width.
  \item Matrix heatmap --- a grid whose cell colour is the value or edge count.
  \item Force-directed graph --- nodes laid out by a physics simulation with weighted links.
  \item Arc diagram --- nodes on a line joined by arcs.
\end{itemize}

\section{User Journey}
\label{sec:user-journey}

The user journey begins when the user connects the system to their live PostgreSQL database. Following the familiar database login of earlier schema-based tools, the interface presents a short connection form in which the user enters the host, the port, the database name, and the user name and password of a database account. The password is used only to open the connection and is never stored or displayed. Once the connection is established, the system automatically inspects the database schema and presents the available tables and columns through the web interface. Each column is labelled with its inferred semantic type, helping the user understand how the system interprets the data before making a selection. The user therefore does not need to inspect the schema manually or write a database query.

The user can express the desired data in either of two ways. In the structured picker, the user first chooses a base table from a drop-down list and then ticks the columns to visualise. The selection can then be refined through several optional controls, none of which requires writing a query.

\begin{itemize}
    \item \textbf{Related columns (join).} A drop-down offers every column reachable from the chosen table through a foreign key, and the \emph{add related column} button brings the selected one into the working set. For example, a user working on the \texttt{borders} table can add each country's continent so that the chart can show or filter on it, even though continent lives in a different table.
    \item \textbf{Filters.} Each filter narrows the rows to those of interest before the chart is drawn, so the chart then describes only the matching rows. For example, a user can keep only European countries or only countries whose population exceeds one million, and the \emph{clear filters} button removes them all at once.
    \item \textbf{Aggregation.} This summarises the rows into groups rather than charting them individually. The user picks one or more \emph{group by} columns, whose distinct values become the groups such as one group per continent, together with one or more \emph{measures} to compute for each group, for example the total population, the average GDP, or a simple count of rows. An optional \emph{resample} step first buckets a numeric or date column into ranges before grouping, for example years into decades or GDP into bands. An optional \emph{having} condition then keeps only the groups whose measure passes a threshold, for example only groups containing more than three countries. A further toggle lets this condition either collapse the rows into the qualifying groups or instead keep the individual rows that belong to those groups, so that the underlying relationship is preserved when the user wants it.
    \item \textbf{Display limit.} The \emph{show top N rows} control restricts a large chart to its leading rows, for example the twenty most populous countries, while the underlying aggregation is still computed over the whole selection rather than over the displayed sample.
    \item \textbf{Goal.} An optional free-text note states the purpose of the chart, for example comparing values across countries or examining the correlation between GDP and unemployment. The system uses it only to tailor which valid chart it recommends first, never to change the data that are retrieved.
\end{itemize}

Alternatively, the user can describe the required data in natural language, after which the system converts the request into the same validated selection used by the structured picker. Both routes therefore produce the same \{table, columns, joins, filters, aggregate\} selection and enter the same run-time pipeline.

Once the selection has been submitted, the system retrieves the required rows, identifies the corresponding visualisation schema pattern, determines the valid chart types, and generates an interactive visualisation. The chart recommended by the LLM is presented first, together with a brief explanation of why it is preferred and why the alternatives may be less suitable. The user can then inspect the other valid candidates and switch between them without repeating the data selection. If a valid chart does not yet have an implemented renderer, the interface displays a clear placeholder message rather than allowing the request to fail without explanation.

This journey is designed so that the user specifies only the data and analytical intent, while the system handles the technical decisions required to retrieve and visualise it. The valid schema patterns, chart types, and field-to-role mappings are defined by the auditable programs behind the interface. The LLM can rank and select only from this predefined candidate space and cannot introduce an unsupported chart or mapping.

The design also separates reproducible processing from subjective recommendation. For a given validated selection, pattern identification and data retrieval always produce the same pattern and rows. Rendering a particular candidate with the same mapping and data also produces the same visualisation. The only deliberately non-deterministic decision is which valid candidate the LLM recommends as the preferred chart. The deterministic core therefore satisfies the reproducibility requirement established in Section~\ref{sec:design-requirements} and provides the configuration evaluated experimentally, while the deployed system retains the flexibility to tailor its leading recommendation to the user's stated intent.

\chapter{Implementation}
\label{ch:implementation}

This chapter describes how the design of Chapter~\ref{ch:approach} was realised, including the technical choices and model-serving infrastructure, the prompt-engineering process, the generated programs, the renderer library, the web front end and production layer with its pushed-down data retrieval, and the problems encountered during development.

\section{Technical Choices and Infrastructure}
\label{sec:impl-tech}

The system is implemented entirely in Python, including both the compile-time scripts that interact with the LLM and the run-time pipeline that executes the generated programs. This choice was motivated by two considerations. First, Python is widely used across the data-processing and machine-learning ecosystems, ensuring the ready availability and straightforward integration of the database toolkit, OpenAI-compatible model clients, and schema-processing utilities required by the project. Second, because the generated programs are also written in Python, the same language can be used throughout the whole system. LLM-generated programs can be imported and executed directly, without requiring cross-language interfaces or foreign-function bindings. 

The compiled programs require an LLM during the authoring stage, and the choice of model evolved over the course of the project. The initial approach was to host open source models locally, motivated by the anticipated cost savings and greater control associated with running inference in house. The \texttt{Qwen} family was selected because it offered strong reasoning and code generation capabilities, could be deployed efficiently through vLLM, and provided models suited to different authoring tasks. Several \texttt{Qwen} models were therefore deployed on the Imperial HPC. Each model exposed an OpenAI compatible API that was accessed through an SSH tunnel. \texttt{Qwen3-14B} was assigned to the classifier and recommender because these components required general reasoning and reliable interpretation of natural language requirements. It also provided a practical balance between model capability and the computational resources available on the cluster. The code specialised \texttt{Qwen2.5-Coder-32B-Instruct} was assigned to the renderers because these components required the generation of longer and more structurally complex executable code.

In practice, however, this approach proved unsatisfactory in terms of both authoring quality and operational convenience. As documented in the cross author study presented in Chapter~\ref{ch:evaluation}, the self hosted models achieved only partial correctness on the more demanding recommender task and responded inconsistently to prompt revisions. Furthermore, the expected convenience of local deployment was outweighed by the operational burden of GPU scheduling, model serving, and the SSH tunnelling required to access the cluster. The open source approach was therefore discontinued after the experimental phase. In the deployed system, \texttt{Claude Sonnet} was selected to author the renderers because these components require reliable generation of relatively complex and executable visualisation code. \texttt{GPT-5.4} was selected for the classifier and recommender because these components place greater emphasis on instruction following, and the consistent production of structured outputs.

All models, whether hosted locally or accessed remotely, use the same OpenAI compatible interface. Consequently, changing the authoring model requires only a configuration change and does not require any modification to the underlying code. This abstraction also allowed the cross author comparisons reported in Chapter~\ref{ch:evaluation} to be conducted consistently. Figure~\ref{fig:impl-serving} illustrates the model serving topology used during the experimental phase.


\phfig{0.8}{Experiment-phase model-serving topology: several Qwen models served by vLLM on the HPC cluster, each exposing an OpenAI-compatible endpoint reached over an SSH tunnel, alongside remote hosted models (GPT and Claude), all addressed through one client interface. The deployed system draws on the remote models; the self-hosted route was retired after the experiments.}{fig:impl-serving}

Alongside this compile-time authoring, the LLM plays a second role at run time. Three features of the deployed system consult an LLM for every request. The natural language front end converts a request expressed in free text into a structured data selection. The chart selection layer then identifies the most appropriate chart from a set of deterministic candidates. Finally, the geographical detection component uses the LLM to determine whether a given column contains geographical data.

These run time operations differ from program authoring because they involve lightweight calls made for individual requests rather than the one time generation of complete programs. Latency and cost are therefore more important than maximum authoring capability, making a smaller and faster model more appropriate. The deployed system uses the hosted \texttt{Qwen3.7-flash} model for all three features. It is accessed remotely through Alibaba Cloud's DashScope API using the same OpenAI compatible interface adopted elsewhere in the system. Using a managed API also avoids the operational burden that made local model serving unsuitable for the authoring stage. No GPU scheduling or model serving infrastructure needs to be maintained. Furthermore, as with every model dependent feature in the system, each of these components falls back gracefully to a deterministic procedure when no API key is configured.

The renderer prompts are organised differently into two layers, because different chart types share a great deal of contract but differ in their particulars. The second layer consists of a separate prompt for each chart type. Since charts differ in their mapping requirements, visual structures, and interaction behaviours, each chart specific prompt describes only the rules and characteristics unique to that chart. When a renderer is authored, the relevant chart specific prompt is concatenated with the shared base prompt and submitted to the LLM, which then generates the rendering code. This layered design keeps the common contract in a single location while allowing the requirements of individual charts to remain independent. It also makes the rendering layer straightforward to extend. Adding a new visualisation type requires only a new chart specific prompt, while the existing base prompt can be reused without modification. The design therefore supports the extensibility requirement introduced earlier.

\section{The Three Generated Programs}

Each pipeline step is realised as a generated standard-library program, and the three programs are written so that their interfaces fit together. The classifier exposes a \texttt{classify\_selection} function that reads the schema with the selected table and columns and returns the predicted pattern. The recommender exposes a \texttt{recommend} function that reads the same selection together with that pattern and the data rows, and returns a set of candidate charts and the one it selects, where each candidate carries a chart name and a mapping from visual roles to column names. Every renderer exposes a \texttt{render} function that reads one such mapping with the data rows and returns a complete HTML document. These interfaces are not incidental, because each one is written into the prompt that authors the program. Figure~\ref{lst:prompt-contracts} shows the clause that fixes each interface, which is why the three programs are designed from the outset to read and produce the shapes that the next stage expects.

\section{The Renderer Library}
\label{sec:impl-renderers}

Every renderer is implemented exclusively using D3~v7 rendering library. D3 was selected because it supports a wide range of standard and custom visualisations while providing direct control over data transformation, graphical elements, and interaction within the browser. This flexibility allows all eighteen chart types to follow a common rendering contract without depending on separate chart specific libraries. At run time, each renderer reads the grouped data identified by the \texttt{table} field in its mapping and produces a complete interactive HTML document with hover tooltips. The same renderer can therefore operate on different datasets and numbers of rows without modification.

The choropleth requires additional processing because geographical visualisation differs from the other chart types. A conventional chart can position values directly according to their numerical or categorical fields, whereas a choropleth must first associate each regional value in the database with a geographical feature on a map. This association is not always straightforward because different datasets may represent the same country using its name, an ISO code, or a numeric identifier.

To preserve generality across different databases, the choropleth renderer does not embed geographical information from any particular dataset. Instead, it uses a general world basemap containing sovereign country boundaries and a generic resolver that joins the input data to the corresponding map features. For each regional value, the resolver attempts to match a normalised country name, an ISO alpha 2 code, an ISO alpha 3 code, or a numeric country identifier. The renderer can therefore operate on any database in which the geographical column contains recognised country names or ISO codes.

The renderer also checks whether the geographical join is sufficiently complete before drawing the map. It reports the proportion of distinct regional values that were successfully resolved and refuses to render the choropleth if this proportion falls below a defined threshold. This safeguard prevents the system from producing a misleading or largely blank map. The server uses the same signal to exclude the choropleth from the recommendations when the selected data are not genuinely geographical. A square root colour scale is applied to prevent a small number of very large values from making the remaining countries appear almost white. Figure~\ref{fig:impl-choropleth} shows the renderer applied to a measure from the Mondial database.

\phfig{0.8}{The database-agnostic choropleth renderer: region values are resolved to basemap features by name or ISO code, a square-root colour scale keeps skewed measures legible, and the renderer refuses to draw when too few regions resolve.}{fig:impl-choropleth}

Interaction is implemented consistently across the renderer library. Every chart provides hover tooltips, while the web front end adds controls for zooming, panning, full screen viewing, and downloading. These controls ensure that dense visualisations, such as matrix heatmaps and force directed graphs, remain easy to explore.


\section{Web Front End and Production Layer}
\label{sec:impl-production}

An interactive web front end connects the compiled programs into a complete pipeline. On the threaded HTTP server, the user selects a table and a set of columns or enters a natural language request. The server then runs the classifier, generates candidate charts, asks the LLM to select the most appropriate candidate, and invokes the corresponding renderer. The resulting interactive visualisation is displayed within a sandboxed iframe. 

A production layer connects this pipeline to external services without modifying the reasoning programs. A data source adapter provides access to a live PostgreSQL database while preserving the schema and row dictionary formats already consumed by the pipeline. It uses schema introspection to recover keys and column types, and executes pushed down queries to retrieve data. Both the data aware experiments and the deployed system access the same live PostgreSQL database through this adapter. The natural language module uses an OpenAI compatible client to convert a request expressed in free text into a validated selection, while continuing to operate through a deterministic fallback when no API key is configured. These production features are controlled through a configuration file excluded from version control and remain confined to the adapter and optional model calls. The classifier, recommender, and renderers therefore require no modification. Across these parts the selection is the pivot that ties them together. A selection is produced either by the structured column picker or by the natural language parser, and it is then turned into rows by the data source adapter through its pushed down query. The remainder of this section describes the production layer in greater detail.

\subsection{Server and Request Flow}

The server exposes a small set of endpoints. One endpoint returns the database schema and the semantic badges assigned to each column for display in the selection interface. A second accepts a structured selection and runs the full pipeline. A third renders a chart again when the user assigns a different column to a visual role, without repeating the reasoning stages. When natural language input is enabled, an additional endpoint accepts a request expressed in free text and returns a parsed selection for the user to review before execution. The execution and repeated rendering endpoints also accept a display top-$N$ value and report both the number of rows displayed and the total number contained in the selection. This allows the user to restrict a large chart to its leading rows without affecting the whole table aggregation performed by the database. Figure~\ref{ fig:impl-sequence} traces a natural language request through the server.

\phfig{0.92}{Request flow for a natural language query. The text is parsed once into a validated selection and presented to the user for confirmation. The server then classifies the pattern, generates candidate charts, asks the LLM to select one, and runs the corresponding renderer on rows retrieved from the live database. The resulting interactive HTML is returned to the user. The LLM is called only to parse the request and select the chart, while classification, retrieval, and rendering remain deterministic.}{ fig:impl-sequence}

\subsection{Data Source Adapter}

The adapter supplies the pipeline with a clean schema dictionary and row dictionaries in the same formats that it already consumes, while obtaining the underlying information from a live PostgreSQL database. Schema introspection recovers primary keys, foreign keys, column types, and unique constraints. A single retrieval method then accepts the complete selection, including the table, columns, filters, joins, and aggregate, and returns both the prepared rows and the total row count. The method constructs one parameterised query using the SQL builder of Section~\ref{sec:impl-pushdown} that performs joining, filtering, and aggregation within the database. Aggregates are therefore computed over the complete table rather than a bounded sample held in memory. The same principle applies to statistics used for filtering, which are calculated in the database through \texttt{MIN}, \texttt{MAX}, and \texttt{COUNT(DISTINCT)}.

Because the adapter returns rows in the format already expected by the pipeline, none of the three pipeline stages required modification when the system was connected to the live database. At present, only a PostgreSQL adapter is implemented. It uses the \texttt{psycopg2} driver and a PostgreSQL specific statement timeout to limit the duration of each query. Other database engines are therefore not yet supported. Nevertheless, the adapter interface and the portable \texttt{SQLAlchemy} introspection on which it is based limit the changes required to support another engine to the implementation of a new adapter and a corresponding SQL dialect for the builder, and the remainder of the pipeline would remain unchanged.

\subsection{Data retrieval and SQL pushdown}
\label{sec:impl-pushdown}

The query that fetches a selection's data is produced by the SQL builder, turning the clean schema and a selection into one parameterised PostgreSQL query. It builds the query in four layers, applied in order: join, filter, aggregate, then order-and-limit. The join layer is a common table expression holding the base table left-joined to each requested column along the shortest foreign-key path, which the builder finds by searching the schema's foreign-key graph. A path that would multiply rows is collapsed to one row per base key with \texttt{DISTINCT ON}. On that expression, each filter becomes a \texttt{WHERE} predicate, an aggregate becomes a \texttt{GROUP BY} with the matching functions (\texttt{SUM}, \texttt{AVG}, \texttt{COUNT}, \texttt{MIN}, \texttt{MAX}), and a display limit becomes a trailing \texttt{ORDER BY}\,/\,\texttt{LIMIT}. Table and column identifiers are validated against the schema and quoted, and every literal value is emitted as a named bind parameter and passed to the driver separately, so a filter value never enters the SQL text. 

\begin{figure}[htbp]
\begin{lstlisting}[style=prompt]
--- selection (input) ---
{ "table":   "country_population",
  "columns": ["country", "population"],
  "filters": [{"column": "year", "op": "range", "min": 1990, "max": 2010}],
  "aggregate": {"group_by": ["country"],
                "measures": [{"column": "population", "fn": "sum"}]},
  "limit":   20 }

--- generated query (output) ---
WITH j AS (
  SELECT b.*
  FROM "country_population" AS b
)
SELECT "country", SUM("population") AS "sum_population"
FROM j
WHERE ("year" IS NOT NULL AND "year" >= :p0 AND "year" <= :p1)
GROUP BY "country"
ORDER BY SUM("population") DESC NULLS LAST
LIMIT :p2
-- params: { p0: 1990, p1: 2010, p2: 20 }
\end{lstlisting}
\caption{The SQL builder in action: a selection and the PostgreSQL query it emits.}
\label{lst:sql}
\end{figure}

Figure~\ref{lst:sql} shows a selection and the single query the builder emits for it. The example combines all three optional stages, and every clause of the emitted query traces back to one field of the selection. The selection asks for the total population of each country between 1990 and 2010, capped at 20 rows. The base table sits in the \texttt{j} CTE, which is trivial here because no join was requested but is always present, so the query has the same shape whether or not a join is needed. The \texttt{year} range becomes the \texttt{WHERE} predicate, which also drops nulls. The aggregate becomes \texttt{GROUP BY "country"} with \texttt{SUM("population")}, and the display cap becomes \texttt{ORDER BY} the measure \texttt{DESC} followed by \texttt{LIMIT}. The three literals \texttt{1990}, \texttt{2010}, and \texttt{20} appear only as the bind parameters \texttt{p0} to \texttt{p2}, never in the query text.

Running the query this way pays off in three ways, all visible in the example. First, it is exact. Since the \texttt{SUM} executes inside the database, it ranges over every matching \texttt{country\_population} row, so each per-country total is complete and correct however large the table grows. Second, it is economical. Only the 20 rows the display needs are returned, not the underlying relation. Finally, it is safe. Because identifiers are validated against the schema, values travel as bound parameters rather than inlined text, and the query runs inside a read-only transaction under a statement timeout, neither a malformed selection nor a hostile filter value can alter, damage, or hang the live database it runs against.

This selection is the same structure that the data source adapter retrieves through the SQL builder of Section~\ref{sec:impl-pushdown}, so the natural language layer only changes how a selection is produced and not what the rest of the pipeline does with it. To make the choice, the model is given a compact view of the schema together with the user request. Each column is annotated with its data type, and the foreign-key graph is summarised as a list of relationship tables so that a request spanning two entities can be mapped onto the connector table that joins them. \end{figure}

Three mechanisms improve the reliability of this process. First, for selections without aggregation, the module deterministically ensures that the primary key columns of the base table are included. This provides the recommender with an identity role and allows it to produce valid candidates. Second, a compact keyword resolver identifies measure columns that are named explicitly in the request and verifies that they remain present in the parsed selection. If the LLM omits one of these columns, the module repeats the request with a correction. This mechanism favours precision over recall. A paraphrase containing no recognisable keyword is therefore passed directly to the LLM without intervention. Third, the parser can be run several times at a nonzero temperature, with the final table and column set determined by majority vote across the resulting selections. In the evaluation, this procedure recovered the single case missed by direct parsing. Before execution, the parsed selection is presented to the user as a plain English summary that can be reviewed and edited.

\subsection{Geographical Detection and Column Switching}
\label{sec:impl-geo}

Two additional mechanisms allow the deployed pipeline to operate beyond the Mondial database. The first identifies geographical columns and determines whether charts such as choropleths or word clouds can be recommended. It applies general heuristics to column names, table names, and foreign key targets, with optional refinement by an LLM. The model can recognise geographical columns that the heuristics overlook, such as a column containing ISO codes but carrying a generic name. The result is computed once for each connected schema and is reused both for the semantic badges displayed in the interface and for the recommendation stage. The information presented to the user therefore remains consistent with the decision made within the pipeline.

The second mechanism allows a user to assign a different compatible column to a visual role after a chart has been rendered. The interface offers only columns with a matching dimension and role type. Identity roles are also supported, allowing a key, region, or text role to be reassigned to another key belonging to the same entity. A user may therefore display a word cloud using country names rather than country codes. Alternative keys are detected generically as columns that are not primary keys but are either declared unique in the schema or found to be distinct and nonnull in the data. This approach allows the mechanism to operate on any connected database. \chapter{Evaluation}
\label{ch:evaluation}

This chapter assesses the system against the objectives set out in Chapter~1. The evaluation is organised around the two distinct ways in which the project uses a language model, because each role calls for a different standard of success. In the first role the model acts as a compiler that authors a deterministic program once, so the question that matters is whether the authored program \emph{executes correctly}, producing the right pattern, the right chart recommendation and mapping, and a runnable visualisation. In the second role the model assists a small run-time step of the live system, such as parsing a natural-language request or selecting a chart, and the natural way to judge this is by the behaviour of the complete pipeline rather than of any one step in isolation.

Section~\ref{sec:eval-setup} states the success criteria and the method common to both parts. Part~A then evaluates the compiler role by execution correctness, covering pattern identification (Section~\ref{sec:eval-step1}) and chart recommendation, mapping, and implementation (Section~\ref{sec:eval-step2}). Part~B evaluates the run-time assistant role end to end on an external, previously unseen task set (Section~\ref{sec:eval-nl}). The chapter closes by reflecting on the determinism, scalability, and extensibility of the design (Section~\ref{sec:eval-determinism}) and on the limitations that bound these results (Section~\ref{sec:eval-limitations}).

\section{Success Criteria and Method}
\label{sec:eval-setup}

The project is successful if a language model can drive the transformation of a data selection, whether chosen directly or expressed in natural language, into a meaningful visualisation, through a pipeline that identifies the conceptual visualisation schema pattern, recommends a suitable chart, and produces a runnable visualisation, without the user having to inspect relational tables by hand. A second criterion applies to the deterministic core. Pattern identification, data retrieval, and rendering are frozen programs, so a given selection must always yield the same pattern, the same rows, and the same rendering of a chosen chart. This reproducibility is what allows each figure reported below to be read as a property of a fixed program rather than of a sampled model response.

\paragraph{Part~A, the compiler role.} Steps~1 to~3 are deterministic programs authored once by a model, so what matters is whether the program \emph{produces correct results when executed}, not how closely its source resembles any reference text. Each step is scored by running the authored program over the evaluation cases and comparing its outputs against the expected answers, with the exact criterion for each step stated at the start of its section. For every step a hand-written \emph{reference} program provides a trusted baseline. It bounds the accuracy attainable on the task, and, compared against an authored program over a wider set of inputs than the headline cases, it exposes structural defects those cases alone may not reveal, such as a program that answers the sampled cases yet fails to restrict its recommendations correctly in general. This comparison too is one of behaviour, not of code text.

\paragraph{Part~B, the run-time assistant role.} The natural-language parser and the chart-selection layer are consulted afresh on each request and their outputs are not deterministic. They are therefore evaluated end to end, by asking whether the whole pipeline turns a free-text request into an acceptable selection, pattern, and chart, rather than by scoring any single call.

\paragraph{Cases, data, and models.} The primary dataset is the Mondial geographical database \cite{mondial}, whose schema exercises every one of the six patterns of Section~\ref{sec:step1} in genuine relations, including basic entities such as \texttt{country} and \texttt{lake}, an inherited-key entity in \texttt{economy}, weak entities such as \texttt{country\_population} and \texttt{ethnic\_group}, a one-to-many link in \texttt{airport}, an ordinary many-to-many in \texttt{encompasses}, and a reflexive many-to-many in \texttt{borders}. Part~A uses nine data-first cases, each a selection of one table together with several of its columns, chosen to cover all six patterns. The programs and the model receive only structural evidence about the schema, namely keys, foreign keys, and column types, while the expected answers are held out from them, as is standard. Because pattern identification reasons only from key structure, it is independent of where the rows live. The data-aware steps instead read their rows from a live PostgreSQL instance of Mondial through the same data-source adapter the deployed system uses, so those results reflect the real data path rather than an offline sample. Part~A also compares several program authors under one fixed evaluation contract, so that runs from different authors are scored identically. Two families of models are used, the self-hosted Qwen models served on the Imperial HPC (\texttt{Qwen3-14B} for the reasoning-heavy pattern and chart steps, and \texttt{Qwen2.5-Coder-32B-Instruct} for renderer generation), and a stronger general model, referred to below as GPT, reached through a university web-chat platform. Part~B is evaluated separately on the external task set introduced in Section~\ref{sec:eval-nl}.

\subsection{Renderer runnability}
\label{sec:eval-step3}

The third compiler-role step authors the renderers. A rendered chart has no single correct output to compare against, since the same data can be drawn faithfully in many ways, so the renderers are judged only on \emph{runnability}, that is on whether a renderer produces a complete, valid document that runs and draws the chart without error. Assessed this way by structural and static JavaScript checks, all eighteen renderers across the five patterns produce complete, runnable documents. The one failure mode seen while developing them was a context-budget one, where an earlier approach that inlined the data into the generation prompt could truncate a long document before it closed. The final two columns of Table~\ref{tab:eval-nl} contrast the chart the LLM highlighted with the gold expectation. The two often agree, but on several tasks the selector prefers a defensible data-aware alternative, choosing a choropleth for a country-keyed measure and a matrix heatmap for the dense many-to-many relations of D7 and D12, where the Sankey is unavailable in any case. The residual misses are informative rather than structural. The two selection misses, D7 and D12, are gold-superset artefacts. The parser chose the right table but left the relationship's scalar attribute \texttt{percentage} out of the selected columns, so the strict column-superset test scores them as misses even though the table is correct, which is why D12 still identifies the right pattern and an acceptable chart. For comparison, David's tool solved 11 of the 13 tasks but needed hand-written custom SQL for seven of them and failed two outright, whereas the pipeline reaches a comparable selection rate directly from free English and, on the two tasks David failed, degrades to a sensible chart rather than crashing.

Two features of the parser account for the relationship tasks in particular. Each column is annotated with a semantic badge, one of numeric, temporal, lexical, or geographical, and the brief ends with an explicit list of relationship tables derived from the foreign-key graph, for example that \texttt{encompasses} connects \texttt{country} and \texttt{continent}. The parser is also run several times at a non-zero temperature, with the table and column set decided by majority vote. Together these let D12, ``how the population of continents is divided between countries'', resolve to \texttt{encompasses} and a many-to-many chart rather than being flattened to a per-country population bar.

The remaining weaknesses are concentrated, as expected, in the filter/join/aggregate layer, which is where Bull's users needed custom SQL. Encouragingly, the parser auto-generated the query structure for most of these from plain English, including geographic filters expressed as a join through \texttt{encompasses}, a multi-value membership filter with a numeric range, and a grouped ``having count'' aggregate, all cases Bull solved only with hand-written SQL. The genuine gaps are top-$N$ ordering and limiting, a temporal ``at some point'' maximum over years, and a derived cross-table threshold. These are natural targets for future work rather than failures of the schema-reasoning core.

\section{Determinism, Scalability, and Extensibility}
\label{sec:eval-determinism}

Finally, the pipeline is assessed against the three requirements that motivated its design (Section~\ref{sec:design-requirements}). Its deterministic components are \emph{reproducible} by construction. Because pattern identification, data retrieval, and rendering are frozen programs, the same selection always produces the same pattern, the same rows, and the same rendering of a given chart. This is precisely what makes the tables above meaningful, since each reported accuracy is a property of a fixed program rather than of a sampled model response. The one run-time judgement the deployed system delegates to the LLM is the choice of chart among the legal candidates (Section~\ref{sec:step2-llm}), a deliberate trade of determinism for the LLM's intent- and data-aware judgement that leaves the deterministic core, and therefore the evaluation, untouched.

It is \emph{scalable} in the sense that matters for this system. Because each renderer reads its data from disk at run time rather than through the prompt, a visualisation is independent of dataset size, which is what dissolves the context-budget failures of Section~\ref{sec:eval-step3} in the deployed pipeline. Mondial itself, with its dozens of tables and its largest relations in the thousands of rows, is served without difficulty, and the data-source adapter draws from a live PostgreSQL database using bounded queries for row retrieval.

It is \emph{extensible} because the components are decoupled through explicit contracts. A new chart is added by authoring one more renderer against the shared \texttt{render(mapping, rows)} signature and adding one entry to the recommender's chart group, without touching pattern identification or any existing renderer. The eighteen charts across five patterns were built incrementally in exactly this way. The database-agnostic mechanisms reinforce this. Geographical columns are detected generically rather than hard-coded to Mondial, the choropleth resolves regions through a generic basemap index and refuses to draw rather than render a blank map when it cannot, and alternative keys are discovered from schema uniqueness or the data itself, so the same pipeline can be pointed at another relational database with no change to its reasoning core.

\section{Limitations and Threats to Validity}
\label{sec:eval-limitations}

The results above are encouraging, but several limitations bound how far they should be read, and they are stated here so that the conclusions of the next chapter can be read against them.

\paragraph{Sample size and a single dataset.} The pattern and recommendation results rest on nine cases, and the end-to-end results on thirteen tasks, all drawn from Mondial. A perfect score on nine cases is evidence that the compiled rules are correct on those cases, not a statistical accuracy over a large population, and the internal-validity strength of a deterministic classifier is bought at the cost of external validity. The approach has been demonstrated on one schema, and its behaviour on unrelated databases is only partially probed by the database-agnostic mechanisms rather than measured.

\paragraph{Provenance of the expected labels.} The expected patterns and tasks are taken from earlier student projects on the same database. Because the prompts were iterated against these very boundary cases, in particular the inherited-key versus weak-entity distinction, there is a risk of over-fitting the specification to Mondial's exact structure. A genuinely unfamiliar schema might surface ambiguities the current prompts do not resolve.

\paragraph{Reproducibility of the strong author.} The self-hosted Qwen results are fully reproducible, but the strong ``GPT'' author was reached through a web-chat platform whose exact model version is not pinned, so that particular provenance comparison cannot be reproduced exactly. It should be read as an existence result, a sufficiently strong model authors a near-correct program in one shot, rather than as a precise benchmark of a named model.

\paragraph{Runnability judged by static analysis.} Renderer correctness was assessed by structural and static JavaScript checks rather than by opening every generated file in a browser and confirming its pixels. These checks catch the failure modes that dominated the study, but they do not guarantee that every chart is visually faithful in every browser.

\paragraph{Qualitative and mixed-run evaluations.} The recommender's handling of the relationship charts and the readability of the renderers were assessed qualitatively, without a user study, so claims about appropriateness and legibility are the author's judgement rather than measured human preference. Finally, the natural-language improvement was a partial, mixed-model re-run in which several tasks were reused from an earlier run, so the reported gain is not a clean single-variable comparison. A full re-run under one model would isolate the effect more cleanly.


\chapter{Ethical Considerations}
\label{ch:ethics}

This chapter discusses the ethical dimensions of the work. Although the project is a research prototype rather than a deployed product, several of its design choices have ethical consequences, and the constrained, deterministic form of the pipeline was in part motivated by them.

\section{Data provenance and privacy}

The primary dataset, Mondial, is a well-documented, publicly available geographical database assembled from public sources such as international statistical yearbooks and encyclopaedias. It contains information about countries, cities, geographical features, organisations, languages, and religions, and no personal data about identifiable individuals. Using it therefore raises no data-protection concerns, and its long history as a teaching and research benchmark makes results on it easy for others to reproduce and scrutinise. The production layer can, however, connect to an arbitrary live PostgreSQL database, which may contain sensitive or personal data. Two properties of the design limit the exposure this creates: the pipeline reads only the schema and the specific rows a selection requires to reason about structure and to render a chart, and, when the natural-language and selection layers are disabled, no data leaves the machine at all. Where a third-party model API is used, any data placed in a prompt is sent to that provider, so a deployment over sensitive data should prefer the self-hosted models, which keep both the schema and the rows within the operator's own infrastructure.

\section{Transparency and the risk of misleading visualisations}

A visualisation is a form of argument, and an automatically generated one can mislead if the mapping beneath it is wrong: a poorly chosen chart, a miscoloured map, or an inverted axis can all suggest a pattern that the data does not support. The design mitigates this in three ways. First, the space of legal charts and their mappings is fixed by deterministic, auditable programs: because each step is a small, readable program rather than an opaque per-case LLM response, a questionable recommendation can be traced to the rule that admitted it, even when the final choice among the legal charts is the LLM's. Second, the pipeline degrades safely rather than silently: the choropleth refuses to draw when too few regions resolve, and a chart without a renderer returns a clear placeholder instead of a broken or empty image. Third, the LLM is deliberately confined at the edges of the pipeline, choosing which data to plot and which of several legal charts to highlight, but never inventing the mapping, so it cannot fabricate a visual claim that the deterministic core would reject. Transparency also brings a reproducibility benefit that matters ethically in a research setting: a reported accuracy is a property of a fixed program, so the evaluation cannot be quietly improved by re-sampling an LLM until it agrees.

\section{Environmental cost}

Serving large language models, even for the modest workload of authoring a handful of programs, consumes energy on shared high-performance computing infrastructure. The LLM-as-compiler paradigm has a favourable profile here that is worth stating explicitly: because the LLM is invoked only once, at compile time, to author each program, and never again while the system serves requests, the per-request energy cost of the deployed pipeline is that of ordinary deterministic code, not of model inference. A system that instead called an LLM on every request would multiply its inference cost by its traffic; this one does not. The one-off authoring cost is small and is incurred only when a new program is created or a prompt is revised.


\chapter{Future Work}
\label{ch:future}

The evaluation of Chapter~\ref{ch:evaluation} points to several natural extensions, which fall into three groups: broadening what the pipeline can express, strengthening the weakest layer, and testing the approach more widely.

\section{Broadening the visualisation vocabulary}

The relationship chart set could be extended with parallel-set and alluvial diagrams and with hierarchical edge bundling, all of which suit dense many-to-many data and would give the data-driven selector a richer menu to rank. Two structural cases in particular are currently unexercised. The first is the \emph{directed} reflexive relation, in which the two endpoints of a self-relationship are asymmetric, such as a river flowing into another; the current arc and chord renderers assume an undirected relation, and directedness would call for arrowed or ordered encodings. The second is the \emph{temporal relationship attribute}, where the strength of an association changes over time; the Mondial schema contains no such attribute, so supporting it would require both a new dataset and an animated or small-multiple encoding. Both were identified during the audit of Mondial as gaps in the test data rather than in the design, and both are good candidates for a follow-up dataset chosen specifically to exercise them.

\section{Strengthening the natural-language and authoring layers}

The natural-language evaluation showed that the weakest layer is the translation of filters, joins, and aggregates from free English: top-$N$ ordering and limiting, a temporal maximum over years, and derived cross-table thresholds were the remaining gaps. These are well-defined targets, and each could be addressed by extending the selection grammar and the parser's few-shot guidance without disturbing the schema-reasoning core. On the authoring side, the non-monotonic response of the weaker model to prompt hardening (Section~\ref{sec:eval-step2}) raises a clear question: whether fine-tuning a smaller model to author these programs would give the reliability that prompt engineering alone could not, and whether it would do so more cheaply than relying on a large general model. A controlled comparison of prompt engineering against fine-tuning for program authoring, holding the target contract fixed, would answer this directly.

\section{Wider evaluation and user studies}
\label{sec:future-engines}

The system was evaluated on Mondial and on an external task set written for an earlier project, but a full test of generalisability would run it against several unrelated databases, measuring how often the geographical detection, the alternative-key discovery, and the pattern classifier behave correctly on schemas they were never tuned for. Reaching those databases would also mean supporting engines beyond PostgreSQL, the only one implemented so far (Section~\ref{sec:impl-pushdown}); because data access is confined behind the data-source adapter, this is a matter of adding a further adapter and a matching SQL dialect for the builder rather than changing the pipeline. Finally, the appropriateness and readability of a visualisation are ultimately judged by people, so a user study, along the lines of those conducted for the two predecessor systems, comparing both expert and non-expert users on the natural-language workflow and on the clarity of the generated charts, would complement the automated evaluation with the human judgement that only a study can provide.


\chapter{Conclusion}
\label{ch:conclusion}

This project set out to investigate whether Large Language Models can support conceptual-model-based data visualisation, asking whether an LLM can reason over relational schema structure, identify the visualisation schema patterns of McBrien and Poulovassilis, recommend suitable visualisations, and drive an end-to-end pipeline from a user's request to a runnable chart. The evaluation of Chapter~\ref{ch:evaluation} answers each of these in turn.

On the first two objectives the results are strong. A generated, deterministic classifier identifies the correct visualisation schema pattern on all nine cases, telling apart the structurally similar inherited-key basic entity and weak entity, and a generated recommender returns the chart set its pattern admits and emits mappings that drive the renderers with no glue code. On the third objective, eighteen renderers spanning five patterns turn those mappings into interactive visualisations, and because each reads its data at run time rather than through the prompt, the context-budget failures of an earlier run-time approach cannot recur. On the fourth objective, the complete natural-language pipeline generalised to an external task set written for an earlier project, parsing the correct data selection on most tasks, identifying the expected pattern on almost all of them, and offering an acceptable chart on every scored task, while degrading gracefully on requests that even the predecessor tool could not express.

The thread running through these results is the LLM-as-compiler paradigm. By asking the LLM to author a deterministic program once, rather than to answer each case at run time, the project turned the two most troublesome properties of run-time LLM use, non-determinism and a bounded context window, from recurring hazards into problems settled once at authoring time. This is what makes the reported accuracies meaningful, since each is a property of a fixed program that returns the same result on every run, and what makes the system extensible, since a new chart is one more renderer authored against a shared contract. It also separates this work from Text-to-SQL, because the natural-language front end performs a constrained, visualisation-oriented semantic parse that chooses only which data to plot and leaves every decision about how to visualise it to the auditable programs behind it.

The approach has clear limits, most of them concentrated in the translation of complex filters and aggregates from free English, and in the reliance on a sufficiently strong model to author the more intricate programs. These are the natural subjects of the future work of the previous chapter. Taken together, the results support the project's central claim, that a Large Language Model can perform conceptual-schema-level reasoning to identify visualisation schema patterns and to drive executable visualisation generation, and that it can do so in a way that is auditable and reproducible in its deterministic core.

\chapter{Example Prompts}
\label{app:prompts}

This appendix reproduces a condensed excerpt of the pattern-identification
prompt (Section~\ref{sec:step1}). Under the LLM-as-compiler paradigm the prompt does
not ask the LLM to answer each case; it asks the LLM to author, once, a
deterministic Python classifier that encodes the rules below. The excerpt has been
shortened and reflowed for the page; the full prompt is kept under version control in
the project repository.

\section{Step 1 --- Pattern-Identification Prompt (Excerpt)}
\label{app:step1-prompt}

\begin{verbatim}
You are an expert in relational databases and ER-model reasoning.

Task: write a deterministic Python program that implements the ER
pattern-identification rules below, so the rules are applied by running
code rather than by reasoning case by case. Reason ONLY from the primary-
key (PK) and foreign-key (FK) structure of a selection, never from the
natural-language meaning of table or column names.

Scope constraint (strict): use only the selected table and selected
columns. A foreign key counts only if its column is selected; a PK column
counts only if it is selected. Never introduce a column the user did not
select.

Pattern rules:
- Basic entity: selected columns contain a PK and attributes, with no
  selected foreign-key dependency.
- Basic entity, inherited key: the WHOLE primary key is inherited as a
  foreign key from one parent (every PK column is a FK to that parent,
  with no local PK column). The single-column case counts.
- Weak entity: compound PK where a proper subset of the key is a FK to a
  single parent and at least one remaining PK column is local to the child.
- One-many relationship: a selected FK to a single parent that is NOT part
  of the table's primary key.
- Many-many relationship: relationship table whose PK is composed of two
  FKs to two SEPARATE parent tables.
- Reflexive many-many: as above, but both FKs reference the SAME parent.

Decision order (apply the first matching rule):
1. PK has >= 2 columns and every PK column is a FK -> many_many
   (different parents) or reflexive_many_many (same parent).
2. Else every PK column is a FK to a single parent (no local PK column)
   -> basic_entity_inherited_key.
3. Else compound PK mixes FK columns and local columns -> weak_entity.
4. Else a selected FK lies outside the PK -> one_many_relationship.
5. Else -> basic_entity.

Required interface: a single self-contained standard-library module,
deterministic (no randomness, no network, no model calls), exposing
classify_selection(schema, table_name, selected_columns) -> dict
returning predicted_pattern and a short reason. It must read blind input
only and must never read any gold/answer file.
\end{verbatim}

\section{Step 2 --- Chart-Recommendation Prompt (Excerpt)}
\label{app:step2-prompt}

The chart-recommendation prompt (Section~\ref{sec:step2}) likewise asks the LLM to author a
deterministic program rather than to recommend charts case by case. The excerpt below
shows the dimension-typing rules and one per-pattern block; the full prompt covers every
pattern and fixes the mapping field names the renderers consume.

\begin{verbatim}
Task: write a deterministic Python program that, given the schema, a
column selection and its identified pattern, (1) classifies each selected
attribute's dimension type, (2) checks every chart in the pattern's group
against its mandatory requirements, (3) lists the eligible charts, and
(4) emits, for each, a mapping whose field names are EXACTLY the ones the
Step-3 renderers consume. Reason only from PK/FK structure and SQL column
types, never from the natural-language meaning of names.

Dimension types (from the SQL type):
- scalar   : INT, INTEGER, BIGINT, NUMERIC, DECIMAL, FLOAT, DOUBLE, REAL ...
- temporal : DATE, TIME, TIMESTAMP, YEAR
- discrete : VARCHAR, CHAR, TEXT
Match by the leading type name, so NUMERIC(10,2) is still scalar.
Two further characters are CONDITIONAL (cannot be proven from the type):
geographical (region key -> choropleth) and lexical (word key -> word cloud);
flag them, do not assert them.

basic_entity / basic_entity_inherited_key:
  key = the selected primary-key column; attributes = selected scalar/
  temporal columns that are not keys.
  - bar     : key + >=1 scalar attribute -> { table, key, measure }
  - scatter : key + >=2 scalar attributes -> { table, key, x, y }
  - bubble  : key + >=3 scalar attributes -> { table, key, x, y, size }
  - calendar: key + >=1 temporal attribute -> { table, date, key }
  - choropleth (conditional: key geographical) -> { table, region, color }
  - word cloud (conditional: key lexical)     -> { table, text, size }
\end{verbatim}

\section{Step 3 --- Base Renderer Contract (Excerpt)}
\label{app:step3-prompt}

Every renderer is authored against the shared base prompt of
Section~\ref{sec:step3}. The excerpt below shows the parts of the contract that proved
decisive in the evaluation: the fixed entry point, the pinned library version with its
list of forbidden removed APIs, and the rule against brace-based templating.

\begin{verbatim}
Write one self-contained standard-library Python module that exposes
    render(mapping: dict, rows: list[dict]) -> str
returning a complete HTML document, plus a --mapping/--data/--out CLI.
The data is supplied at run time as a file; it is NOT embedded in this
prompt, and the program must not assume any dataset, value set, or row count.
Always read column names from the mapping; never hard-code Mondial names.

Library (pinned): D3 version 7 only, from the official CDN. Do NOT use
APIs removed in D3 v6+ -- d3.keys, d3.values, d3.entries, d3.map, d3.set,
d3.nest, d3.event -- use Object.keys, Map, Set, d3.group/d3.rollup, and the
event passed as the first argument to listeners.

Do NOT assemble the HTML with any brace-based templating (no f-strings, no
str.format): the embedded JavaScript contains literal { ... } and ${ ... }.
Inject JSON only by plain string concatenation or str.replace on non-brace
placeholder tokens, and keep all JavaScript braces exactly as written.

The visualisation must be interactive: hovering a mark shows a tooltip and
emphasises the connected marks. Handle empty data by rendering a short
"No data to display" message rather than a NaN layout.
\end{verbatim}
